# USDM_MindMap_Editor UI 設計書

作成日: 2026-07-15

## 1. 目的

本書は、USDM_MindMap_Editor の画面構成、操作、ノード表示、ダイアログ、状態表示を定義する。

## 2. 基本方針

- マインドマップ感覚で要求と仕様を編集できること
- ノード追加操作を少なくし、入力に集中できること
- ID はユーザーが手入力せず、自動採番すること
- YAML への保存結果が Git 管理しやすいこと
- ノード間の関係が一目で分かること

## 3. 画面構成

```text
┌──────────────────────────────────────────────┐
│ ツールバー                                    │
├──────────────────────────────────────────────┤
│                                              │
│                 キャンバス                    │
│                                              │
│  背景 / 上位要求 / 下位要求 / 仕様ノード       │
│                                              │
├──────────────────────────────────────────────┤
```

## 4. ツールバー

初期実装で想定する操作:

| 操作 | 内容 |
|---|---|
| 新規 | 空の USDM 文書を作成する |
| 開く | YAML ファイルを読み込む |
| 保存 | YAML ファイルをブラウザのダウンロードとして保存する |
| 背景追加 | 背景項目を追加する |
| 検索 | 要求、理由、仕様を検索する |
| エクスポート | メニューから USDM 表へ変換してダウンロードする |
| ズームリセット | キャンバスを100%表示へ戻し、パン位置を初期化する |

ノード構造が変わった場合と YAML 読み込み後は、自動整列を実行する。手動でノード位置を調整する操作は提供しない。

Fit All と Fit Selection は将来対応とし、初期版ではズームリセットを提供する。

## 5. キャンバス

キャンバスは以下を満たす。

- 無限スクロール相当の広い作業領域
- ドラッグによるパン
- ホイールまたは UI 操作による25%から200%のズーム
- 1操作あたり10%を基本単位とするズーム
- 自動整列・自動配置されたノードの表示
- 接続線の表示
- ノード選択状態の表示

新規文書の初期表示は100%とする。ホイールでズームする場合はポインター位置を中心とし、ポインターが指していたキャンバス上の位置がズーム前後で可能な限り同じ画面位置に残るように表示する。保存済み文書を開く場合は、保存されたズーム倍率とパン位置を復元する。配置と座標変換の詳細は [LayoutDesign.md](LayoutDesign.md) を参照する。

## 6. ノード種別

### 背景ノード

表示項目:

- ID
- 背景本文

背景ノードはサブツリーの最上部に表示する。上位要求は背景ノードの下へ右にインデントして表示し、背景ノードの下辺周辺の追加領域から作成する。複数背景は左辺を揃え、サブツリー全体が重ならないよう上から下へ並べる。

### 上位要求ノード

表示項目:

- ID
- 要求
- 理由

操作:

- 下位要求追加
- 編集
- 削除
- 理由の展開・折りたたみ

### 下位要求ノード

表示項目:

- ID
- 要求
- 理由

操作:

- 仕様追加
- 編集
- 削除
- 理由の展開・折りたたみ

### 仕様ノード

表示項目:

- ID
- 仕様
- 関連する下位要求数

操作:

- 編集
- 削除
- 関連する下位要求の設定

仕様の関連する下位要求は、所属先とは別の参照としてノード内に件数を表示する。親子接続線は所属先の下位要求との間だけに表示する。

### 配色

初期版の配色は以下とする。

| 対象 | 配色 |
|---|---|
| 背景ノード | 青 |
| 要求ノード | 緑 |
| 仕様ノード | 黄 |
| ノードの文字と枠線 | 黒 |
| キャンバス | 白 |

配色のユーザー設定は将来対応とする。

## 7. ノード配置

初期表示での配置方向:

- 親ノードを上に、子ノードをその下へ右にインデントして配置する
- 子ノードの左辺を、親ノードの水平方向の中心と右端の中間位置へ揃える
- 同じ親を持つ子ノードは左辺を揃え、上から下へ並べる
- 次の兄弟ノードは、先の兄弟の子孫・接続線を含むサブツリー全体の下へ配置する
- 複数背景と同じ親を持つ兄弟ノードは、v1.0 では ID 昇順で表示する
- 放射型や従来の横方向の階層別配置への切り替えは初期版では提供しない
- ノード内容や表示状態が変わっても、ノード同士が重ならないことを優先する

兄弟サブツリー間（複数背景を含む）の上下余白は32px、親の下辺と最初の子の上辺の上下余白は96px、キャンバス外周は96pxを初期値とする。水平位置は親の幅に合わせて決め、親子を上下に離して重複を避ける。必要な場合は上下間隔を広げる。正式な共通幅が280pxなら、子の左辺は親の左辺から210px右の位置となる。

v1.0 では背景、上位要求、下位要求、仕様を共通の固定幅で表示する。可変幅と種類別固定幅は採用しない。正式な初期幅は `240px`、`280px`、`320px` の UI 比較後に確定し、`280px` を暫定実装値かつ第一候補とする。

幅の比較では、短い要求、2〜3行の通常要求、長い要求と理由、英数字を含む要求、4階層表示時のキャンバス占有量、ノード高さ、可読性、画面内情報量を確認する。正式決定前は `280px` を確定値として扱わない。

すべてのノードは最低 `110px` の高さを確保する。操作ボタンや接続操作などの領域は、初期値として高さ `32px` を確保し、UI 確認後に調整できるものとする。

手動並べ替えは v1.0 では提供しない。将来手動順を保存する場合は手動順を優先し、同順位は ID 昇順、手動順がないノードも ID 昇順で安定して表示する。詳細な配置規則は [LayoutDesign.md](LayoutDesign.md) を参照する。

階層と表示方向（各階層で下へ進み、右へインデントする）:

```text
背景
    上位要求
        下位要求
            仕様
```

## 8. ノード追加操作

### 下辺周辺の追加領域

子ノードの追加は、親ノードの下辺に沿う細い操作領域から行う。ノード内に独立した追加ボタンや＋ボタンは表示しない。

| 親ノード | 下辺周辺から追加する子 |
|---|---|
| 背景 | 上位要求 |
| 上位要求 | 下位要求 |
| 下位要求 | 仕様 |
| 仕様 | 追加対象なし。追加領域を設けない |

- 領域は下辺全幅に沿う3〜4px程度の帯とし、初期値は画面上の4 CSS pxとする。下辺を中心に内側2px、外側2pxを基本とする。
- ズーム25〜200%でも画面上の厚さを維持する。ノード幅とともに横方向へ追従する。
- ホバー時は下辺のみを強調し、ポインターカーソルと「上位要求を追加」「下位要求を追加」「仕様を追加」のツールチップを表示する。強調によってノード寸法や配置を変えない。
- マウス主ボタンの単一クリック、またはトラックパッドの通常クリックで、そのノードを親とする入力ダイアログを開く。右クリックでは追加しない。あらかじめ親を選択しておく操作は不要とする。
- ダイアログの保存で入力を検証し、IDを採番して子を追加する。キャンセルや入力エラーだけでは文書へノードを追加しない。
- 接続線の起点と追加領域が重なっても、下辺のクリックを受け付ける。接続線自体のクリックでは追加しない。
- 本文、理由の展開部、編集・削除操作をクリックしても子追加を起動しない。追加領域からのドラッグをパンや追加として扱わない。
- ダイアログが開いている間の連打で、ダイアログやノードを重複生成しない。
- 領域はキーボードフォーカス可能とし、フォーカス時も位置を強調する。`Enter`または`Space`で同じ追加操作を実行できるようにする。読み上げ名はツールチップと同じ操作名を使用する。

背景自体の追加は従来どおりツールバーの「背景追加」から行う。子追加領域の画面座標による判定と操作競合の詳細は [LayoutDesign.md](LayoutDesign.md) §9.3・9.4を参照する。

2026-10-27実装状況：下辺帯、3種の子追加、背景追加、入力ダイアログ、必須入力・親階層・関連下位要求の検証を実装済み。理由は任意、仕様の関連先は所属先を除く下位要求から複数選択する。ダイアログはモーダルとし、キャンセルまたはEscapeでは追加せず、終了時に起点へフォーカスを戻す。子追加領域の通常表示には文字・＋記号を置かず、ホバー・フォーカス時だけ下辺を強調する。試験履歴は [QA_Q_sheet.md](QA_Q_sheet.md) D-14を参照する。

### 上位要求追加

```text
背景ノードの下辺周辺の追加領域をクリックする
  ↓
入力ダイアログ表示
  ↓
要求、理由を入力
  ↓
保存
  ↓
選択した背景を親とする上位要求ノード生成
```

### 下位要求追加

```text
上位要求ノードの下辺周辺の追加領域をクリックする
  ↓
入力ダイアログ表示
  ↓
要求、理由を入力
  ↓
保存
  ↓
下位要求ノード生成
```

### 仕様追加

```text
下位要求ノードの下辺周辺の追加領域をクリックする
  ↓
入力ダイアログ表示
  ↓
仕様を入力
  ↓
保存
  ↓
仕様ノード生成
```

上位要求、下位要求、仕様の追加時に親を複数選択する操作は提供しない。

ノード追加後は自動レイアウトを実行し、追加ノードと既存ノードが重ならない位置へ表示する。ノードの追加、編集、削除、理由の展開では、影響するサブツリーを再配置し、関係のないノードを不必要に移動させない。YAML 読み込み時は文書全体を自動配置する。

## 9. 入力ダイアログ

### 要求入力

項目:

- 要求
- 理由

入力ルール:

- 要求は必須
- 理由は任意
- ID は表示のみ、または保存後に自動表示する

### 仕様入力

項目:

- 仕様
- 関連する下位要求（任意、複数選択）

入力ルール:

- 仕様は必須
- ID は表示のみ、または保存後に自動表示する
- 所属先の下位要求は `parent_requirement_id` として必ず1つ保存する
- 関連する下位要求は `related_requirement_ids` として保存し、所属先と同じ下位要求は選択できない

### 背景入力

項目:

- 背景

入力ルール:

- 背景は必須

## 10. ノード削除

親ノードを削除する場合は、配下の子要素をすべて削除する。削除確認ダイアログには削除対象のノード数を表示する。

確認ダイアログには「今後この確認を表示しない」チェックボックスを置く。選択結果はブラウザに保存し、以降の削除では確認ダイアログを表示しない。設定は将来の設定画面から再有効化できるようにする。

## 11. ノード検索

検索対象は要求、理由、仕様とする。ID は検索対象に含めない。

- 要求検索: 要求本文を対象に検索する
- 理由検索: 理由本文を対象に検索する
- 仕様検索: 仕様本文を対象に検索する
- フリーワード検索: 要求、理由、仕様を横断して検索する

検索結果では一致したノードを一覧表示し、選択するとキャンバス上の該当ノードを強調表示する。

## 12. 理由の表示

理由はデフォルトで折りたたんで表示する。
上位要求と下位要求の右端に V ボタンを配置し、押下時に理由を展開または折りたたむ。
展開中は理由の全文をノード内に表示する。
保存済み文書を開く場合は、ノードごとに保存された理由の展開・折りたたみ状態を復元する。
理由の展開によってノードサイズが変わる場合は、影響するサブツリーと接続線を必要な範囲で再配置する。

子ノードを非表示にするサブツリー折り畳みは、理由の表示切り替えとは別の将来対応機能とする。

## 13. エクスポート時の警告

YAML 保存では、理由が空でも警告を表示しない。
USDM 表、Excel などのファイルエクスポート時は、理由が空の要求を警告一覧に表示する。
警告は出力を妨げず、ユーザーは確認後にダウンロードを続行できる。

## 14. 接続線

接続線は SVG で描画する。

- 線種: ベジェ曲線
- 矢印: 親から子へ向かう方向を表示
- 子ノードへの接続位置: 親ノードの下辺中央から出る
- 親ノードからの接続位置: 子ノードの左辺中央に入る
- 選択中ノードに関係する線を強調表示

背景、上位要求、下位要求のいずれも、子ツリーへの線は下側から曲線で伸ばす。複数の子ノードがある場合も、同じ下辺中央を起点として各子ノードの左辺中央へつなぐ。子ノードを持たないノードには、子向けの接続線を表示しない。

子は親の下へ配置し、曲線は親の下辺から下方向へ出て、親の中心と右端の中間に揃えた子の左辺へ滑らかに入る見え方とする。理由の展開や本文の変化でノード高さが変わった場合も、子と後続サブツリーを必要な範囲で下へ移動し、接続線を新しい下辺・左辺へ追従させる。詳細は [LayoutDesign.md](LayoutDesign.md) の配置規則・接続線設計を参照する。

ベジェ曲線は親子関係の接続線にだけ使用し、関連する下位要求への参照には接続線を表示しない。

関連する下位要求を線で表示する機能を将来追加する場合は、親子接続線とは別の関連リンクとして表示する。

## 15. ステータスバー

表示候補:

- 現在の YAML ファイル名
- 未保存変更の有無
- ノード数
- ズーム率
- 検証エラー件数

## 16. キーボード操作

初期候補:

| 操作 | キー |
|---|---|
| 保存 | `Cmd+S` |
| Undo | `Cmd+Z` |
| Redo | `Cmd+Y` |
| コピー | `Cmd+C` |
| ペースト | `Cmd+V` |
| 選択ノード削除 | `Delete` |
| ズームリセット | `0` |

コピーとペーストは macOS 版でのみ提供する。Windows 版の `Ctrl+C`、`Ctrl+V` は初期版では実装しない。

## 17. 大規模データ時の表示

多数のノードを含む文書でも、画面に表示されていないノードの文書データは失わない。論理レイアウトと画面上の描画対象を分離し、将来、ビューポートと一定の周辺余白を優先して描画できるようにする。周辺余白の具体値は性能試験と操作確認後に決定する。

ビューポート外非描画は v1.0 の必須機能とはせず、2,000ノードの性能試験が目標未達の場合に v1.0 の投入候補として再評価する。サブツリー折り畳みは将来対応とする。検索結果や選択対象へ移動する際の表示・ズーム動作も今後決定する。

v1.0 は2,000ノードを実用的な操作性の性能評価対象とする。2,000ノードを超える文書も開けるが、v1.0 の性能保証対象外とする。10,000ノード以上は YAML の保存・読み込み目標であり、全件を同時描画して快適に操作できることを意味しない。

2,000ノードでは、初回表示2秒以内、ノード追加200ms以内、ノード編集200ms以内、局所レイアウト500ms以内、YAML 保存1秒以内を設計上の初期目標とする。パンとズームは60fpsを目標とし、平均45fps以上かつ30fps未満の状態が継続しないことを目指す。瞬間的な低下だけでは不合格とせず、正式な保証値は性能試験後に確定する。将来ノードドラッグを追加した場合も同じ連続操作の評価対象とする。

一次性能評価は macOS / Apple Silicon M2 / Google Chrome 最新安定版で行う。Safari 最新版は互換性と実動作を確認する。メモリは読み込み、操作、クローズを反復しても使用量が増加し続けないことを確認し、絶対上限値は実測後に決定する。

## 18. 手動配置

初期版ではノードのドラッグ移動を提供せず、ノードは自動レイアウトで配置する。

手動配置、「自動配置へ戻す」操作、親ノード移動時の子ノード追従は将来対応であり、操作仕様は未決定とする。
