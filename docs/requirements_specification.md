# USDM_MindMap_Editor

## 概要

USDM（Universal Specification Describing Manner）の要求仕様を
マインドマップ形式で整理・編集できるアプリケーション。

目的は

- 要求整理
- 要求の階層化
- 要求→仕様へのトレーサビリティ
- Git管理可能なテキスト形式での保存

を実現することである。

---

# 基本コンセプト

- ノードを追加するだけでUSDMを作成できる
- マインドマップ感覚で編集できる
- YAML形式で保存する
- IDは自動採番する
- 保存後も人間が読めるデータ形式とする

---

# データ構造

## 背景

項目

- ID
- 背景

ID

`001`～`65535`（`001`～`999` は3桁ゼロ埋め、`1000`～`65535` はそのまま表記）

最大65535件

背景はマインドマップの最上位ノードとする。
上位要求は必ず1つの背景に属し、複数の背景を親に持つことはできない。
`000` はアプリケーションでは使用しない。

- 要求

ID形式

- 仕様

親ごと65535件

所属先以外の下位要求は、関連する下位要求として任意に記録できるが、親にはならない。

# 保存形式

YAML

例

```yaml
backgrounds:

  - id: "001"
    text: 顧客が簡単に操作できること

requirements:

  - id: "001"
    request: 操作はマウスだけで完結する
    reason: 誰でも利用可能にするため
    parent_background_id: "001"

  - id: "001-001"
    request: 左クリックのみで編集可能
    reason: 学習コスト削減
    parent_requirement_id: "001"

  - id: "002"
    request: 編集内容を失わない
    reason: 入力途中の作業を保護するため
    parent_background_id: "001"

  - id: "002-001"
    request: 編集内容を自動保存できる
    reason: 入力途中の作業を保護するため
    parent_requirement_id: "002"

specifications:

  - id: "001-001-001"
    specification: 左クリックで入力ダイアログ表示
    parent_requirement_id: "001-001"

  - id: "001-001-002"
    specification: ダブルクリック不要
    parent_requirement_id: "001-001"
    related_requirement_ids:
      - "002-001"
```

# UI

## キャンバス

無限スクロール

キャンバスはドラッグによるパンが可能

キャンバスは25%から200%の範囲でズーム可能とし、初期表示は100%とする。

ホイールなどによるズームは、1操作あたり10%を基本単位とする。

ポインター操作でズームする場合は、ポインターが指していたキャンバス上の位置を、ズーム前後で可能な限り同じ画面位置に維持する。

100%表示へ戻すことができる。

YAML を保存して再度開いた場合は、保存時のズーム倍率とパン位置を復元する。

マインドマップ形式で表示する

ノード位置は保存せず、ノードの追加、削除、YAML 読み込み後に自動整列・自動配置する。
ノードを手動で移動する機能は初期版では提供しない。

背景、上位要求、下位要求、仕様を、親の下へ子を並べ、階層が深くなるごとに右へインデントするマインドマップとして表示する。子ノードの左辺は、親ノードの水平方向の中心と右端の中間位置へ揃える。同じ親の子は上から下へ並べ、次の子は先の子のサブツリー全体より下へ表示する。放射型などの別レイアウトへの切り替えは初期版では提供しない。

複数背景と同じ親を持つ兄弟ノードは、v1.0 では ID 昇順で安定して表示する。将来、手動の表示順が保存される場合は手動順を優先し、手動順がないノードは ID 昇順とする。

v1.0 では全種類のノードを共通の固定幅で表示する。可変幅と手動並べ替えは提供しない。

ノードの内容や表示状態が変化した場合も、ノード同士が重ならず視認可能となるよう配置する。

ノードの追加、編集、削除、理由の展開などの通常操作では、影響する範囲を再配置し、関係のないノードを不必要に移動させない。YAML 読み込みなど、全体再配置が妥当な場合は文書全体を再配置できる。

初期版では自動レイアウトを使用し、手動配置は将来対応とする。配置規則、座標系、再配置範囲の詳細は [LayoutDesign.md](LayoutDesign.md) を参照する。

理由の展開・折りたたみ状態は、要求本文とは分離したビュー状態として保存し、YAML を再度開いたときに復元する。

## 大規模データ時の表示

保存形式上の ID 上限、保存・読み込み可能なノード数、画面上で快適に操作できるノード数は別の要件として扱う。ID 上限までの表示性能を保証するものではない。

v1.0 は10,000ノード以上を保存・読み込み可能なデータ量の目標とする。10,000ノードすべてを同時描画して快適に操作できることは、v1.0 の性能保証に含めない。

v1.0 は2,000ノードを実用的な操作性の性能評価対象とする。2,000ノードを超える文書の使用は禁止しないが、性能保証対象外とする。

2,000ノードに対する設計上の初期性能目標は、初回表示2秒以内、ノード追加200ms以内、ノード編集200ms以内、局所レイアウト500ms以内、YAML 保存1秒以内とする。パンとズームなどの連続操作は60fpsを目標とし、平均45fps以上かつ30fps未満の状態が継続しないことを初期目標とする。正式な v1.0 保証値は基準環境での性能試験後に確定する。

性能評価ではブラウザメモリの絶対上限を事前に固定せず、文書の読み込み、操作、クローズを繰り返してもメモリ使用量が一方向に増加し続けないことを確認する。

大規模データ対応では、保持している文書データを失うことなく、表示対象をビューポート周辺など必要な範囲へ絞れる構造とする。ビューポートカリングを v1.0 で実装するかは性能試験後に判断する。

サブツリーの折り畳みによる表示対象の制御は将来対応とする。

## 子ノード追加の共通操作

背景、上位要求、下位要求から子ノードを追加するときは、親ノードの下辺中央を中心とする楕円形の領域をクリックする。縦の全長は画面上10px、横の範囲は親ノードの左端から下辺長の1/4の位置から3/4の位置までとする。独立した追加ボタンや＋ボタンは表示しない。ズーム時も画面上の縦10pxを維持し、横幅はノード幅に追従する。

クリックしたノードを親として入力ダイアログを開き、入力の保存時に子を作成する。キャンセル時は追加しない。楕円内では、上側に重なる理由の展開・折りたたみ操作より子追加を優先し、理由の表示状態を変えない。楕円外では理由操作を通常どおり行える。子追加操作からパンを開始しない。仕様ノードには子追加操作を設けない。背景自体の新規追加は、従来どおりツールバーから行う。表示と判定領域の詳細は [UI.md](UI.md) §8、[LayoutDesign.md](LayoutDesign.md) §9.4を参照する。

子追加領域の強調は一時的な操作案内とし、追加完了を示す青い印として残さない。マウス・トラックパッド起点の保存・キャンセル後は通常表示へ戻し、新たに楕円へポインターを合わせた場合に再度強調する。キーボードでの追加を継続できるよう起点へのフォーカス復帰と視認可能なフォーカス表示は維持する。

# 接続

背景 → 上位要求 → 下位要求 → 仕様

接続線はベジェ曲線で表示する。

子ノードへ伸びる接続線は、親ノードの下辺から出し、子ノードの左辺につなぐ。背景から上位要求、上位要求から下位要求、下位要求から仕様まで同じ接続規則を使用する。

子ノード自体を親ノードの下へ右にインデントして配置し、親の下辺から伸びる曲線を子の左辺へつなぐ。ノードと接続線が重ならず、親子関係を上から下へ追えることを優先する。配置と接続位置・曲線の詳細は [LayoutDesign.md](LayoutDesign.md) を参照する。

# 編集

可能

- ノード追加
- ノード編集
- ノード削除

削除しても他ノードのIDは変更しない。

# 保存

保存形式

YAML

拡張子

.yml

初期版ではブラウザのダウンロードとして保存する。
Google Drive からの作成・保存は将来対応とする。
理由が空でも、YAML 保存時には警告を表示しない。
同じ文書は、固定のキー順、ID順、インデント、改行コードで保存し、内容と無関係な差分を作らない。
`version` には最終保存時のソフトウェアバージョンを記載する。
YAML 構造の互換性を判定する `format_version` は、ソフトウェアバージョンとは別に記載する。機能追加だけでは `format_version` を変更せず、互換性上意味のある YAML 構造変更時だけ更新する。

ズーム倍率、パン位置、理由の展開状態を初めて永続化するリリースでは、SemVer の Minor バージョンを上げる。具体的なソフトウェアバージョン番号はリリース計画で決定する。

# 読込

YAMLファイルを読み込み、
要求、仕様、関連情報を復元したうえで自動整列・自動配置する。

古い YAML 形式を読み込んだ場合は、`format_version` に対応する読み取り用クラスで現在の内部モデルへ変換して表示する。`format_version` がない既存形式は形式バージョン1として扱う。
変換後に保存する場合は、`version` を現在のソフトウェアバージョン、`format_version` を現行形式の値へ更新する。

ビュー状態を持たない旧形式は、ズーム100%、パン位置 `(0, 0)`、理由を折りたたんだ既定状態で読み込む。

# エクスポート

エクスポートメニューから USDM 表へ変換し、ダウンロードできるものとする。
USDM 表、Excel などのファイルエクスポート時に理由が空の要求がある場合は警告を表示する。
警告を確認したうえで、エクスポートは続行できるものとする。
