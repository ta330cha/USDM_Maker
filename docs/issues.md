## 背景単位の配置・追加・移動（2026-10-27実装）

- 空白のダブルクリックで背景入力を開き、保存時に指定位置へ背景を作成する。ツールバーからの追加も維持する。
- 背景本体のドラッグで、その背景と全子孫・接続線をまとめて移動する。子追加楕円の操作を優先し、パンや個別ノード移動と区別する。
- ツリー同士の重複は禁止する。重複する位置でドラッグを終了した場合は開始位置へ戻し、他ツリーは動かさない。
- 子追加・理由展開・実測サイズ変更による拡大時は、操作元の背景位置を維持して他ツリーを自動移動する。2026-10-28に右側の衝突は右、下側の衝突は下へ押し出す方式を実装した。方向不明時の補完は暫定ルールのまま利用評価を続ける。本文編集・削除UIは今回追加していない。
- 背景左上のキャンバス座標を `view.background_positions` に保存する。子孫座標は保存せず、内部は自動配置する。形式3を追加し、形式1・2の変換を維持する。
- `DocumentEditingSession` が文書・ビュー・背景位置を一括確定し、失敗時の部分更新を防ぐ。変更背景を再計算し、未変更背景のツリーを再利用する。細粒度の局所再計算とRevision付き実測キャッシュは未実装である。
- Serializerは位置不足を許容して構造を読み取り、Session/Layoutが初期補完・重複補正を行う。形式3の保存は全背景の確定位置を必須とし、Serializer内で配置を変更しない。保存・開くUIは利用者が指定した今回の範囲に含めず、Coreまでの対応とする。

新規Core/JavaScript自動テストを追加済み。今回のSafari実UI確認の詳細・制約は [QA_Q_sheet.md](QA_Q_sheet.md) に記録し、過去のChromium結果は流用しない。今回Chromeは利用者指定により使用しない。

詳細は [LayoutDesign.md](LayoutDesign.md) §4〜7・9.5、[DataModel.md](DataModel.md) §4・8・11、[UI.md](UI.md) §8・18を参照する。#004の決定を更新し、#005・012・019・021・024へ関連内容を反映する。#026のUndo範囲と#027の離脱確認は引き続き未決定であり、新規番号は採番しない。

## 自動重複解消の方向変更（2026-10-28実装）

右側で重なる他ツリーは右へ、下側で重なる他ツリーは下へ押し出す。右移動でY座標、下移動でX座標を維持する。操作元の固定、全子孫・接続線の同量移動、自動移動した位置の保存は維持する。背景ドラッグ時の重複拒否・開始位置復元は変更しない。

`BackgroundPlacementService.ResolveCollisions` へ変更前矩形の固定スナップショットを渡し、連鎖する各衝突で方向を選び直す処理を実装した。同時衝突は配置優先順で1組ずつ解消し、移動後に全障害物を再検証する。変更前情報がない読込補正や斜めの衝突では、右・下の必要移動量が短い方向、同量は下という暫定ルールを使う。補完ルールの確定・実UI評価は#005で継続し、新規Issue番号は採番しない。詳細は [LayoutDesign.md](LayoutDesign.md) §7.3.1・7.3.2、今回の試験結果と実UIの未確認範囲は [QA_Q_sheet.md](QA_Q_sheet.md) を参照する。過去の下方のみの結果は履歴として維持し、YAML項目と形式3は変更しない。

## 子ノード追加操作の変更（2026-10-27）

子追加は、背景・上位要求・下位要求の下辺中央を中心とする楕円をクリックして入力ダイアログを開く。縦の全長は画面上10 CSS px（上側5px・下側5px）、横の範囲は親の下辺の1/4の位置から3/4の位置までとする。ズーム時も縦10pxを維持し、横幅はノード幅の1/2へ追従させる。独立した追加ボタン・＋ボタンは表示しない。

楕円内で理由の展開・折りたたみと重なる場合は、子追加を優先して理由状態を変えない。楕円外では理由操作を通常どおり受け付ける。外接長方形の四隅は追加対象にしない。

クリックした親に対応する子を入力保存時に追加し、キャンセルでは追加しない。仕様ノードには領域を設けない。背景自体の追加はツールバーに加え、空白ダブルクリックにも対応した。従来の4px帯から楕円形状へ変更した際の理由操作優先制御、入力検証・採番、配置・接続更新は維持する。ドラッグ許容値は画面上4 CSS pxを維持する。旧仕様と楕円仕様の試験履歴は [QA_Q_sheet.md](QA_Q_sheet.md) D-14、詳細は [UI.md](UI.md) §8と [LayoutDesign.md](LayoutDesign.md) §9.3・9.4を参照する。背景単位より細かい局所再計算、Safariと利用者環境での操作感評価は残課題とし、新しいIssue番号は採番しない。

追加後に青い楕円が残る利用者報告について、Safari 27.0でフォーカス復帰後の`:focus-visible`単独による塗りつぶしを実測した。2026-10-27に入力方法別の表示と残留解除を実装した。マウス起点の保存・取消・Escape後は強調を解除し、新しいポインター移動で最新の楕円内を確認してから再開する。起点へのフォーカス復帰は維持し、キーボード起点は輪郭で操作位置を示す。JavaScript29件とCore77件は成功した。Safari実UIの一部条件は引き続き確認が必要であり、全受け入れ条件を完了扱いにはしない。Chromeは今回の利用者指定に従い試験対象から外した。今回も新規Issue番号は採番せず、確認範囲・制約は [UI.md](UI.md) §8と [QA_Q_sheet.md](QA_Q_sheet.md) D-14で管理する。

# Issue #003 仕様の共有

## 現状

仕様は1つの下位要求に属する前提。

しかし

```
要求A
   \
    \
    仕様
    /
要求B
```

というケースが存在する。

## 決定

仕様は必ず1つの下位要求に属するものとする。
複数の下位要求を親として設定することは認めない。

所属先以外の下位要求との関係は、所有関係ではなく任意の関連情報として保存できる。
YAML では `related_requirement_ids` に関連する下位要求 ID を配列で保存する。
この関連情報は仕様の親子関係や ID 採番を変更しない。

```yaml
specifications:
  - id: "001-001-001"
    specification: 編集内容を一定時間ごとに保存する
    parent_requirement_id: "001-001"
    related_requirement_ids:
      - "002-001"
```

## 検討事項

仕様を共有可能にするか。

## 優先度

高

## 状態

決定済み

# Issue #004 ノード座標保存

## 現状

従来は全ノードの座標を保存しない方針だったが、2026-10-27に背景単位の配置位置を保存する設計へ変更し、Coreの形式3保存・読込と背景移動へ反映した。ファイル保存・読込UIは今回未接続である。

## 決定

背景単位の配置位置を、要求データから分離した `view.background_positions` に保存する。値は背景左上のキャンバス座標であり、ズーム・パンとは独立する。ツリー内部の子孫座標は保存せず、背景位置と要求構造から自動計算する。

背景本体のドラッグでツリー全体を移動する。重複する移動先は確定せず開始位置へ戻す。子追加・編集・理由展開などで拡大した場合は他ツリーを自動移動し、その位置も保存する。個別ノードの手動移動は将来対応とする。

## 保存形式

```yaml
view:
  background_positions:
    "001":
      x: 120
      y: 350
```

形式3へ追加し、形式1・2は初期配置で補完する。詳細は [DataModel.md](DataModel.md) を参照する。

# Issue #005 自動レイアウト

## 現状

2026-10-27の添付図に合わせ、親を最上部、子の左辺を親幅の3/4へ置く下方インデント配置を実装した。現在は背景の保存位置を優先し、ツリー内部の範囲を再利用して兄弟を配置する。設定は親子上下96px、兄弟32px、外周96px。背景単位の部分再計算と重複解消を追加し、DOM実測後も配置を更新する。正式幅のUI比較、実測差分閾値の適用、より細粒度の局所再計算とLayoutRevision付き実測キャッシュは残課題である。

## 決定

初期版は自動整列かつ自動配置とする。
ノードの追加、削除、YAML 読み込み後にツリー内部を再計算し、背景配置位置を基準に描画する。背景単位のツリー全体移動を提供し、個別ノードの手動配置は提供しない。拡大時のツリー間重複は他ツリーの自動移動で解消する。

2026-10-28に自動移動を右側の衝突は右、下側の衝突は下へ押し出す方式へ変更した。すべて下へ動かす方式は過去の実装・試験履歴として扱う。斜め・旧データ等の方向補完は暫定設計として検討を継続する。配置内部の方向判定詳細は [LayoutDesign.md](LayoutDesign.md) §7.3を正本とし、実装状況は同書§17.1へ記載する。

親をサブツリーの最上部へ置き、子は親の下へ配置する。子の左辺は親の水平方向の中心と右端の中間（親の左辺から親幅の3/4）へ揃える。兄弟は同じ左辺位置で上から下へ並べ、次の兄弟を先の兄弟の子孫・接続線を含むサブツリー全体の下へ置く。

親子上下間隔は96px、兄弟サブツリー間の上下間隔は32pxを初期値とする。従来の横方向の階層間隔を子のX座標へ加算せず、親幅からインデントを算出する。配置式と再計算範囲は [LayoutDesign.md](LayoutDesign.md) §5・6を正本とする。

同じ親を持つ兄弟ノードは、ID セグメントを数値比較した昇順で表示する。背景は保存位置を優先し、ID順は位置未保存時の初期配置に使用する。v1.0 は手動並べ替えを提供しない。将来手動順を追加する場合は手動順を優先し、未設定のノードは ID 昇順とする。

v1.0 は全ノード種別で共通の固定幅を使用し、可変幅と種類別固定幅は採用しない。正式な初期幅は `240px`、`280px`、`320px` の UI 比較後に確定し、`280px` を暫定実装値かつ第一候補とする。

UI 比較では、短い要求、2〜3行の通常要求、長い要求と理由、英数字を含む要求、4階層表示時のキャンバス占有量、ノード高さ、可読性、画面内情報量を確認する。

高さ予測の初期係数は1行18文字、操作領域高さの初期値は32px、最小ノード高さは110pxとする。18文字は UI 上の文字数制限ではない。予測高さと DOM 実測後の有効高さはいずれも110pxを下回らない。

将来の手動表示順は `displayOrder`（概念上 `int?`、YAML は `display_order`）で保持する。設定済みノードを値の昇順、同値を ID 昇順、その後に未設定ノードを ID 昇順で並べる。v1.0 では保存せず、手動並べ替え UI も提供しない。

ノード高さは表示内容から予測し、必要なノードだけ DOM 実測値で補正する。予測値と実測値の差が `max(8px, 予測高さの10%)` を超える場合だけ、影響するサブツリーを局所再レイアウトする。詳細は [LayoutDesign.md](LayoutDesign.md) を参照する。

# Issue #008 理由の表示方法

## 現状

## 決定

# Issue #019 YAMLフォーマット

# Issue #022 大規模データ対応

## 現状

数百～数千ノードでの動作未定。

## 現時点の方針

- v1.0 は10,000ノード以上を YAML で保存・読み込み可能なデータ量の目標とする。
- v1.0 は2,000ノードを実用的な操作性の性能評価対象とする。
- 2,000ノードを超える文書の使用は禁止しないが、v1.0 の性能保証対象外とする。
- 保存可能件数と快適な同時描画件数を分離し、10,000ノードすべての快適な同時描画は保証しない。
- ビューポートカリングを後付けできるよう、論理レイアウトと UI 描画対象を分離する。
- ビューポートカリングは v1.0 の必須機能とはせず、2,000ノードの性能試験が目標未達の場合に v1.0 の投入候補として再評価する。将来のカリングはビューポート周辺に余白を持てる構造とし、余白値は今回確定しない。
- 一次性能評価環境は macOS / Apple Silicon M2 / 16GB / Google Chrome 最新安定版とする。Safari 最新版は互換性と実動作を確認し、Edge と Firefox は v1.0 の厳密な性能保証対象外とする。

2,000ノードに対する設計上の初期目標は、初回表示2秒以内、ノード追加200ms以内、ノード編集200ms以内、局所レイアウト500ms以内、YAML 保存1秒以内とする。パンとズームは60fps、平均45fps以上、30fps未満が継続しないことを目標とする。瞬間的な低下だけでは不合格とせず、正式な保証値は性能試験後に確定する。

100、500、1,000、2,000ノードの測定用データで描画、自動レイアウト、YAML 読み書き、FPS、メモリ使用量を計測する。メモリは起動直後、2,000ノード読み込み後、操作後、文書クローズ後に測定し、読み込みとクローズ、編集と Undo / Redo、追加と削除の反復で一方向に増加し続けないことを確認する。絶対上限値は実測後に決定する。10,000ノード以上では保存・読み込みの完了とデータ欠落がないことを確認する。

ID は自動採番すると決定しているが、ノード削除によって生じた欠番を再利用するか、常に最大番号の次を採番するかが未定義。
Git 差分の読みやすさや、文書外で ID を参照している場合の追跡性に影響する。

## 暫定決定

初期実装では、各採番範囲内で `001` から探索し、未使用の最小 ID を採番する。
正式決定まで、この挙動を Core 層の単体テストで固定する。

## 検討事項

- 欠番を再利用するか
- 削除済み ID を文書内に履歴として保持する必要があるか
- YAML 外部からの ID 参照を保証対象とするか
