# USDM_MindMap_Editor レイアウト設計書

作成日: 2026-08-10

## 1. 目的

本書は、USDM_MindMap_Editor におけるノード配置、座標系、接続線、ズーム、パン、自動レイアウト、背景単位のツリー全体移動、および大規模データ時の描画制御を定義する。

対象範囲は、USDM 文書の論理的な親子関係を、マインドマップとして配置・描画する処理である。要求内容、YAML スキーマ、画面上の文言や操作部品そのものは本書の主対象としない。

レイアウト方向、座標変換、配置間隔、サイズ計算、接続線計算、再レイアウト条件の詳細は本書を正本とし、他の設計書には各文書の責務に必要な要約だけを記載する。

### 1.1 他設計書との責務分担

| 文書 | 責務 |
|---|---|
| [requirements_specification.md](requirements_specification.md) | 実現する機能と要求を定義する |
| [architecture.md](architecture.md) | レイヤー構成、コンポーネント責務、依存関係を定義する |
| [DataModel.md](DataModel.md) | 保存対象データと内部データ構造を定義する |
| [UI.md](UI.md) | ユーザーに見える情報と操作結果を定義する |
| [issues.md](issues.md) | 未決定事項、決定内容、対応状態を管理する |
| 本書 | ノードと接続線を配置・描画・再配置する規則を定義する |

### 1.2 記載区分

本書では、各方針を次の区分で扱う。

| 区分 | 意味 |
|---|---|
| 確定 | 既存の要求仕様書または Issue で決定済み |
| 実装確認 | 現行コードで確認できる事実 |
| 暫定設計 | 実装開始に必要な推奨案であり、正式決定前 |
| 将来拡張 | 初期版では実装しないが、将来の対応を妨げないよう考慮する事項 |
| 未決定 | 判断材料または合意が不足している事項 |

## 2. レイアウト設計の基本方針

### 2.1 確定事項

- USDM の背景、上位要求、下位要求、仕様の関係を、親子関係が視覚的に追えるマインドマップとして表示する。
- 初期版はツリー内部を自動整列・自動配置し、背景本体のドラッグによるツリー全体移動を提供する。上位要求、下位要求、仕様の個別移動は提供しない。
- 背景単位の配置位置をプロジェクトのビュー状態として YAML に保存する。子孫ノードの座標は保存せず、背景位置を基準に再計算する。
- キャンバスの空白をダブルクリックして背景を追加できる。ツールバーからの背景追加も維持する。
- 異なる背景のツリー同士は重ねない。ドラッグの移動先が重複する場合は、ドラッグ開始時の位置へ戻す。
- 子ノード追加、編集、理由展開、サイズ補正によってツリーが拡大する場合は、他ツリーを自動移動して重複を解消する。
- 親子接続線は、親ノードの下辺中央から子ノードの左辺中央へつなぐベジェ曲線とする。
- 背景、上位要求、下位要求、仕様を、親の下へ右にインデントしながら配置する。子の左辺は、親の水平方向の中心と右端の中間位置へ揃える。
- ノード間隔とキャンバス余白は一元管理するレイアウト設定値とする。
- ズーム範囲は25%から200%、初期値は100%とし、ポインター位置を中心にズームする。
- ノードサイズは予測値を基本とし、必要な場合だけ DOM 実測値で補正する。
- 通常の追加、編集、サイズ変更では、影響するサブツリーを局所的に再レイアウトする。
- v1.0 の兄弟ノードは ID 昇順で配置する。背景は保存済み位置を優先し、位置がない背景だけ ID 昇順で初期配置する。
- v1.0 の全ノードは、種類によらず共通の固定幅を使用する。
- DOM 実測値の有意差判定、サイズキャッシュ、ズーム操作量は設定値として管理する。
- 背景配置位置、ズーム倍率、パン位置、理由の展開状態は、要求データと分離したプロジェクトのビュー状態として保存する。

### 2.2 設計原則

- 要求本文の編集とレイアウト計算を分離し、文書データが描画方式へ依存しないようにする。
- レイアウト計算と UI 描画を分離し、同じ入力から再現可能な配置結果を得られるようにする。
- ノードの論理構造、レイアウト結果、ビューポート状態を別の状態として扱う。
- ツリー内部の自動配置と背景単位の配置位置を分離し、背景移動で親子関係や内部配置を変更しない。
- 保存可能なノード数と、同時に快適に描画できるノード数を分離して扱う。
- ノード数が増えた場合に、全件再計算と全件 DOM 描画だけに依存しない構造とする。

## 3. 論理レイアウト構造

### 3.1 基本親子構造

親子関係は次の木構造とする。

```text
背景
 ├─ 上位要求
 │   ├─ 下位要求
 │   │   ├─ 仕様
 │   │   └─ 仕様
 │   └─ 下位要求
 └─ 上位要求
```

確定済みの関係は次のとおりである。

- 1つの背景は複数の上位要求を持つことができる。
- 上位要求は必ず1つの背景に属する。
- 下位要求は必ず1つの上位要求に属する。
- 仕様は必ず1つの下位要求に属する。
- 上位要求、下位要求、仕様の複数親は認めない。
- 標準の親子レイアウトは木構造として計算する。

### 3.2 関連する下位要求

仕様の `related_requirement_ids` は、所属先以外の下位要求への横断参照である。親子関係、ID 採番、標準のツリーレイアウトには影響させない。

初期版では関連下位要求への接続線を表示しない。将来表示する場合は、親子接続線とは別の関連リンク層として扱い、ツリーの配置結果を変更しない方針とする。

## 4. 座標系

現行実装はCoreのレイアウト結果をHTMLノードとSVGへ共通の座標系で描画し、ブラウザ側の変換でズーム・パンを行う。ノード変更時の局所再レイアウトは編集操作実装時に接続する。

### 4.1 座標モデル

| 座標・状態 | 内容 | 管理責務 |
|---|---|---|
| キャンバス座標 | レイアウトエンジンが計算する論理座標。ズームやパンの影響を受けない | Core のレイアウト処理 |
| 背景配置位置 | 背景ノードの左上を表すキャンバス座標。ツリー全体の基準位置として保存する | プロジェクトのビュー状態 |
| ツリー内相対座標 | 背景の左上を `(0, 0)` として求めるノード・接続線の位置 | Core のレイアウト処理 |
| ノード座標 | キャンバス上のノード矩形の左上座標とサイズ | レイアウト結果 |
| ビューポート座標 | ブラウザ内の表示領域を基準とする座標 | Web UI |
| ズーム倍率 | キャンバス座標を表示倍率へ変換する係数 | `CanvasState` |
| パンオフセット | キャンバス原点をビューポート上で移動する量 | `CanvasState` |
| 接続線座標 | 親子ノード矩形から求める始点、終点、制御点 | 接続線計算処理 |

座標変換は次のとおりとする。

```text
viewportX = canvasX * zoom + panX
viewportY = canvasY * zoom + panY

canvasX = (viewportX - panX) / zoom
canvasY = (viewportY - panY) / zoom
```

HTML ノードと SVG 接続線は同じキャンバス座標系に置き、共通の変換を適用する。これにより、ズーム・パンだけでは個々の接続線座標を再計算しない構造を推奨する。

背景単位の配置とドラッグでは次の関係を使用する。パンによる画面移動と、背景配置位置の変更を混同しない。

```text
nodeCanvasPosition = backgroundPosition + nodeLocalPosition
dragCanvasDelta = pointerViewportDelta / zoom
candidateBackgroundPosition = dragStartBackgroundPosition + dragCanvasDelta
```

背景位置は有限の小数座標とし、負の座標も扱える構造とする。全体描画範囲は全ツリーの最小・最大座標から求め、負座標でもノードと線を切らない。描画範囲確保のために保存位置を一律にずらさない。

描画側で負座標を収める内部オフセットを使用する場合は、HTMLとSVGへ共通に適用し、ポインターからの逆変換にも反映する。この描画上の補正は背景位置やパンの保存値に混入させず、上記の座標変換は論理キャンバスに対して維持する。

ポインター位置をズーム中心とする場合は、ズーム前にポインターが指すキャンバス座標を求め、ズーム後も同じビューポート位置になるようパンオフセットを更新する。

```text
canvasPoint = (pointerPosition - oldPan) / oldZoom
newPan = pointerPosition - canvasPoint * newZoom
```

### 4.2 座標の単位と精度

- キャンバス座標の単位は CSS pixel 相当を暫定案とする。
- 計算途中は小数を許可し、描画時に不要な丸めを行わない。
- ID はノード識別子であり、座標や表示順を表す値として使用しない。

## 5. ノード配置規則

### 5.1 配置方向

基本レイアウトは、親の下へ子を並べ、階層が深くなるごとに右へインデントする方式とする。2026-10-27の添付図による配置方針として、従来の左から右への階層別配置を本方式へ変更する。

```text
[背景]
      [上位要求A]
            [下位要求A-1]
                  [仕様A-1-1]
      [上位要求B]
            [下位要求B-1]
```

図は配置順の模式図であり、ノード幅と間隔の縮尺を表さない。

- 親ノードをサブツリーの最上部へ置き、最初の子ノードの上辺は親ノードの下辺より下へ置く。親を子ノード群の高さの中央へ配置しない。
- 子ノードの左辺のX座標を、親ノードの中心X座標と右端X座標の中間へ揃える。子ノード自身の中心をこの位置へ合わせる意味ではない。
- 同じ親を持つ兄弟ノードの左辺を同じX座標へ揃え、ID昇順で上から下へ並べる。
- 次の兄弟は、先の兄弟の子孫と接続線を含むサブツリー全体の下へ配置する。孫ノードを兄弟ノードの間へ重ねない。
- 子にも同じ規則を再帰的に適用し、背景から仕様まで下方への流れと右へのインデントで要求分解を追えるようにする。
- 背景は保存済み配置位置へ置き、ツリー内部だけに同じ配置式を適用する。配置位置がない背景は外周余白を基準に、既存ツリーと重ならない空き位置へ初期配置する。
- 出口は親の下辺中央、入口は子の左辺中央とし、3次ベジェ曲線でつなぐ。
- 放射型、従来の横方向の階層別配置などへの切り替えは初期版の対象外とする。

ノード矩形の左上を `(x, y)`、幅を `width`、高さを `height` とした配置式は次のとおりとする。

```text
parentCenterX = parent.x + parent.width / 2
parentRightX  = parent.x + parent.width
child.x       = (parentCenterX + parentRightX) / 2
              = parent.x + parent.width * 3 / 4

firstChild.y  = parent.y + parent.height + parentChildVerticalGap
nextChild.y   = previousChildSubtree.bottom + siblingGap
```

`previousChildSubtree.bottom` は先の兄弟サブツリーの全ノード・全接続線と親からその兄弟への接続線を含む最下端とする。曲線やノードに追加の余白が必要な場合は、X座標の整列規則を維持して上下間隔を広げる。

共通幅280pxの場合、1階層ごとの右方向の移動量は210pxとなる。この210pxは幅から計算する例であり固定設定値ではない。正式幅が240pxなら180px、320pxなら240pxとなる。水平投影上で親子の矩形範囲が重なることを許容し、上下の配置で実際の矩形重複を防ぐ。

### 5.2 兄弟順序

v1.0 は、同じ親を持つ兄弟ノードを ID 昇順で安定して表示する。各 ID セグメントを数値として比較し、例えば `999` を `1000` より前に配置する。背景の ID 昇順は位置未保存時の初期配置順であり、保存済み位置やドラッグ後の上下・左右関係を ID 順へ戻さない。

ユーザーによる手動並べ替えは将来対応とする。将来、表示順情報を導入する場合は `displayOrder`（概念上の型は `int?`、YAML キーは `display_order`）を使用する。

表示順は次の規則で決定する。

1. `displayOrder` が設定されたノードを `displayOrder` 昇順で並べる。
2. 同じ `displayOrder` のノードは ID 昇順で並べる。
3. `displayOrder` が未設定のノードは、設定済みノードの後で ID 昇順に並べる。

手動並べ替えを行っていないノードには不要な `displayOrder` を保存しない。v1.0 では `displayOrder` を保持せず、ID 昇順だけを使用する。値の割り当て方法と並べ替え UI は将来実装時に決定する。

### 5.3 間隔と余白

ノード間隔とキャンバス余白は固定値を各処理へ分散させず、レイアウト設定値として一元管理する。初期値は次のとおりとする。

| 設定 | 初期値 |
|---|---:|
| 兄弟サブツリー間の上下間隔／背景自動配置の軸方向間隔 | 32px |
| 親の下辺と最初の子の上辺の最小上下間隔 | 96px |
| キャンバス外周余白 | 96px |

これらはアプリケーションのレイアウト設定値であり、初期版の文書 YAML には保存しない。将来の利用状況に応じて変更できる構造とする。ノード同士の重複回避を優先し、必要な場合は設定値より広い間隔を使用できる。

既存の階層間隔96pxは、新方式では親子の上下間隔へ適用する。従来の `parent.Right + LevelGap` による子のX座標算出は使用しない。子の水平位置は§5.1の親幅から算出する規則を使用する。

v1.0 は背景、上位要求、下位要求、仕様に共通の固定幅を使用し、可変幅と種類別固定幅は採用しない。ノード幅はレイアウト設定値として一元管理し、将来、種類別固定幅へ拡張できる構造を許容する。

正式な初期幅は UI 比較後に確定する。`280px` を暫定実装値かつ第一候補とし、`240px`、`280px`、`320px` で少なくとも次を比較する。正式決定までは `280px` を確定値として扱わない。

- 短い要求
- 2〜3行程度の通常要求
- 長い要求と長い理由
- 英数字を含む要求
- 4階層を下方へインデント配置した場合のキャンバス占有量
- ノード高さ、可読性、画面内情報量

### 5.4 ノード重複回避

レイアウト処理は次の順序で行う。

1. 表示対象ノードと親子構造を確定する。
2. 各ノードの有効な表示サイズを決定する。
3. 子孫を含むサブツリーの必要領域を末端から計算し、キャッシュする。
4. 親をサブツリーの最上部に置き、子サブツリーを順番に下へ配置する。接続線の張り出しを必要領域へ含める。
5. 同じツリーの次の兄弟を先行サブツリーの下へ置き、背景配置位置を加算する。
6. 接続線を含む描画範囲とノード矩形を検証し、ツリー間の重複は§7.3に従って処理する。

サブツリーの高さを単純な親子の最大値で求めず、親ノード高さ、親子上下間隔、子サブツリー群の高さ、兄弟間隔を積み上げる。曲線がその範囲を超える場合は張り出しを加味する。同じ子孫の占有量を祖先ごとに繰り返し全件走査せず、計算済みのサブツリー範囲を使用する。

### 5.5 ノードサイズ計算

ノードサイズは、予測サイズを基本とし、利用可能な DOM 実測サイズがある場合は実測値を優先するハイブリッド方式とする。

```text
ノード内容
  ↓
予測サイズ算出
  ↓
初期レイアウト
  ↓
DOM 描画
  ↓
必要なノードだけ実測
  ↓
差が無視できない場合だけ局所再レイアウト
```

有効サイズの優先順位は次のとおりとする。

```text
DOM 実測サイズ（有効なキャッシュがある場合）
  ↓ なければ
予測サイズ
```

### 5.6 予測サイズ

- DOM が存在しない初回レイアウトでも全ノードのサイズを算出できるようにする。
- ノード幅は全種別共通の固定幅とし、レイアウト設定の `NodeWidth` を使用する。
- ノード高さは、明示的な改行数、固定幅での折り返し行数、表示項目、余白、操作領域から予測する。
- 要求、理由、仕様の長さに応じて高さが変わることを許容する。

初期レイアウトでは次の式を使用する。

```text
ContentWidth = NodeWidth - (HorizontalPadding * 2)

EstimatedContentHeight =
    (VerticalPadding * 2)
  + IdAreaHeight
  + SectionGap
  + (TextLineCount * LineHeight)
  + ReasonAreaHeight
  + OperationAreaHeight
  + OtherVisibleFixedAreaHeight

EstimatedHeight = max(EstimatedContentHeight, MinNodeHeight)

ReasonAreaHeight =
  ReasonExpanded の場合:
    SectionGap + (ReasonLineCount * LineHeight)
  それ以外:
    0
```

本文と理由は明示的な改行ごとに分割し、各行について1行あたりの概算文字数から折り返し行数を求める。日本語表示を主対象とした初期予測係数は `EstimatedCharsPerLine = 18` とする。これは UI 上の入力制限や1行18文字での強制改行ではなく、DOM がない段階の高さ予測にだけ使用する。実際の折り返しとの差は必要なノードの DOM 実測で補正する。

| 設定 | 初期値 | 区分 |
|---|---:|---|
| 左右余白 | 16px | 暫定設計 |
| 上下余白 | 12px | 暫定設計 |
| 行高 | 22px | 暫定設計 |
| ID 領域高さ | 24px | 暫定設計 |
| セクション間隔 | 8px | 暫定設計 |
| `EstimatedCharsPerLine` | 18文字 | 初期予測値 |
| `OperationAreaHeight` | 32px | 初期設定値 |
| `MinNodeHeight` | 110px | 確定した最低高さ |

`OperationAreaHeight` は、操作ボタン、接続操作など常時表示する操作 UI の領域として高さ予測へ含める。UI 確認後に調整できる設定値とし、各ノード実装へ個別に埋め込まない。

子追加用の下辺中央の楕円領域は§9.4のオーバーレイとして扱い、`OperationAreaHeight`とは別に管理する。楕円の縦10pxを予測高さやDOM実測のノード寸法へ加算せず、下辺の接続アンカー位置も変えない。既存の操作領域高さ32pxは、子追加ボタンを表示するための必須余白という意味ではない。

短文ノードであっても `MinNodeHeight = 110px` を下回らない。これはマインドマップ全体の視認性と接続線位置の安定性を保つための UI 上の最低高さである。

### 5.7 DOM 実測とキャッシュ

DOM 実測は次の場合に限定する。

- 初回描画後に補正が必要なノード
- 本文を変更したノード
- 理由の展開など、サイズに影響する表示状態を変更したノード
- 予測値と実測値の差が無視できないノード

実測サイズは実行時キャッシュへ保持し、サイズ条件が変わらない限り再測定しない。全論理ノードの一括 DOM 測定を通常動作にはしない。

DOM 実測値を採用する場合も、レイアウトで使用する高さは次のとおり最低高さを維持する。

```text
EffectiveMeasuredHeight = max(MeasuredHeight, MinNodeHeight)
```

高さの実測差分閾値は次の式とし、設定値として管理する。

```text
Threshold = max(8px, EstimatedHeight * 10%)

abs(MeasuredHeight - EstimatedHeight) > Threshold
```

上記条件を満たす場合だけ差を有意と判断し、影響するサブツリーを局所再レイアウトする。閾値以下の差ではレイアウトを補正しない。幅は v1.0 で固定するため、実測幅が設定幅から外れた場合は設定または CSS の不整合として扱う。

キャッシュ識別情報は概念的に次の組とする。

```text
NodeKey
LayoutRevision
NodeWidth
ReasonExpanded
```

背景 ID と上位要求 ID は同じ値を取り得るため、`NodeKey` はノード種別と `NodeId` の組で一意にする。本文、理由、またはその他のサイズに影響する内容を変更した場合は、ノード単位の実行時 `LayoutRevision` を更新して旧キャッシュを無効化する。ノード幅または理由の展開状態が変わった場合も、キーの変化によって再測定する。

`LayoutRevision` とサイズキャッシュは実行時情報であり YAML へ保存しない。将来、フォントサイズやテーマが寸法へ影響する場合は、必要な値をキャッシュ識別情報へ追加できる構造とする。

入力中のキー操作ごとに再測定と全体レイアウトを行わず、編集確定または一定時間のデバウンス後に反映する。

## 6. 自動レイアウト

### 6.1 実行タイミング

| 操作 | 方針 | 区分 |
|---|---|---|
| 新規文書の初回表示 | 全体レイアウトを行う | 確定 |
| YAML 読み込み | 全体レイアウトを行う | 確定 |
| 背景のドラッグ | 内部レイアウトを再計算せず、対象ツリーを平行移動して重複を検証する | 確定 |
| ノード追加 | 影響するサブツリーを再計算する | 確定 |
| ノード編集 | サイズが変わる場合に影響するサブツリーを再計算する | 確定 |
| ノード削除 | 影響するサブツリーを再計算する | 確定 |
| DOM 実測サイズの反映 | 予測値との差が閾値を超えた場合に影響するサブツリーを再計算する | 確定 |
| 理由の展開・折りたたみ | サイズが変わるノードと影響サブツリーを再計算する | 確定 |
| サブツリーの折り畳み・展開 | 対象サブツリーと祖先側の必要領域を再計算する | 将来拡張 |
| Fit All | レイアウト結果が古い場合は全体再計算を許可する | 将来拡張 |
| 明示的な全体自動整列 | 全体再計算を行う | 操作の提供時期は未決定 |
| 全体構造を大きく変更する操作 | 全体再計算を許可する | 確定 |

### 6.2 全体再計算と部分再計算

初回表示と YAML 読み込みでは全体再計算を許容する。通常のノード追加、編集、削除、実測サイズ変更では、変更ノード、その親、兄弟、および影響するサブツリーだけを再計算する。

下方への配置では、高さの差分を同じツリー内の後続兄弟へ反映する。変更元の背景位置を維持し、他ツリーは重複する場合だけ§7.3に従って移動する。IDが後という理由だけでは他の背景を一律に動かさない。既定幅が変わらない本文・理由編集では、§5.1の水平整列位置を維持する。

部分再計算でツリー内部の重複を解消できない場合は、背景単位、文書全体へ計算範囲を広げる。全体計算を行う場合も背景の確定位置を入力とし、重複解消に必要な背景以外の配置位置を初期化しない。

```text
変更ノード
  ↓
直接の親・兄弟・子孫を再計算
  ↓ 解消不可
背景単位のサブツリーを再計算
  ↓ 解消不可
文書全体を再計算
```

### 6.3 再現性

同じ文書構造、背景配置位置、ノードサイズ、レイアウト設定、折り畳み状態からは、同じ座標を生成する。ブラウザの描画順や列挙順に依存しない決定的な計算とし、Core 層の単体テスト対象にする。

## 7. 手動配置

### 7.1 背景単位の配置

背景本体の主ボタンドラッグで、その背景、全子孫、ツリー内の全接続線を同じ量だけ平行移動する。内部の相対位置、親子関係、ID、兄弟順は変えない。背景単独のツリーも対象とする。下辺の子追加楕円、編集・削除などの操作部品、入力欄はドラッグ開始対象から除外する。

開始位置を確保し、画面上の移動量がドラッグ判定値を超えてから移動する。初期値は既存の4 CSS pxを利用し、子追加楕円の縦寸法とは分離したWeb UI設定とする。ドラッグになった操作の終了時に本文編集や子追加を発火させない。

### 7.2 確定と取り消し

- ドラッグ中は移動候補だけを表示し、保存対象の背景位置は変更しない。他ツリーはドラッグに合わせて移動させない。
- 重複候補は移動不可と分かる表示にする。離した位置で重複がなければ背景位置を確定する。
- 重複する位置で離した場合は、背景・子孫・接続線をすべてドラッグ開始時の位置へ戻し、移動できなかったことを通知する。「直前の重複しない候補位置」への吸着ではない。
- `Escape`、ポインターキャンセル、キャプチャ喪失、画面非アクティブ化では確定せず開始位置へ戻す。ドラッグ中のズーム・パンは併発させない。
- 確定前の保存には候補位置を混入させない。無効移動・取り消し・実質移動なしで新たな未保存変更や履歴を作らない。
- 背景位置を変更した場合は保存対象の変更として扱う。Undo / Redoの履歴範囲と単位は既存Issue #026で決定する。

### 7.3 ツリー間の重複判定と自動移動

異なる背景を根とするツリーは、全ノード矩形と実際の接続線の描画範囲（線幅を含む）を囲む外接矩形で重複判定する。外接矩形内部の空き部分への別ツリーの差し込みも、初期設計では重複とする。ホバー楕円、ツールチップ、選択装飾、影など一時表示は占有範囲へ含めない。矩形内部の共通領域がある場合を重複とし、境界の接触だけは重複としない。自動配置時は設定された背景間隔を確保する。

判定には画面外を含む全ツリーの論理的な占有範囲を使用し、DOMに見えている範囲だけで判断しない。ドラッグ中にサイズ補正などで判定前提が変わる場合は、そのドラッグを取り消してから補正し、古い範囲で移動を確定しない。

| 発生契機 | 対処 |
|---|---|
| 背景ドラッグ | 重複する移動候補は確定せず、開始位置へ戻す。他ツリーは動かさない |
| 子追加、本文編集、理由展開、DOMサイズ補正などによる拡大 | 操作元の背景位置を維持し、他ツリーを必要な範囲で自動移動する |
| 背景追加 | 指定位置または既定の空き位置を基準に配置し、重複を解消する |
| 縮小・削除 | 他ツリーの空白を自動で詰め直さず、確定位置を維持する |
| YAML読込 | 保存位置を基準に再計算し、環境や表示サイズの差で生じる重複を自動解消する。補正があれば通知し、次回保存に反映する |

#### 7.3.1 衝突方向に応じた押し出し（2026-10-28方針変更）

**確定方針:** 操作元のツリーは固定し、右側で重なる他ツリーは右へ、下側で重なる他ツリーは下へ平行移動する。右へ押し出す場合はY座標を、下へ押し出す場合はX座標を維持する。衝突するすべてのツリーを一律に下へ移動する従来の暫定方針は採用しない。この変更は自動重複解消に適用し、§7.2のドラッグ先重複時の開始位置復元は変更しない。

方向判定には背景オブジェクト単体の位置や画面上の中心ではなく、ノードと接続線を含むツリー外接矩形を使う。ズーム・パンに依存しないキャンバス座標で判定する。

**方向判定の設計:** 固定側をA、押し出す側をBとする。変更前の確定レイアウトで、BがAの右側にありY方向の投影が重なっていた場合は右、BがAの下側にありX方向の投影が重なっていた場合は下を選ぶ。変更後の外接矩形で既に重なっていることだけを理由に、位置関係を失わせない。

```text
rightSideBefore = B_before.left >= A_before.right
               && B_before.top < A_before.bottom
               && B_before.bottom > A_before.top
belowSideBefore = B_before.top >= A_before.bottom
               && B_before.left < A_before.right
               && B_before.right > A_before.left

rightSideBefore が true: 右へ
belowSideBefore が true: 下へ
どちらでもない / 変更前の矩形がない: 次の暫定ルールへ
```

**暫定設計（斜め・旧データ等の補完）:** 右下の斜めにあって両方向で分離していた場合、新規背景追加、読込補正など変更前の矩形がない場合、左・上側や既に重なった不正配置など上記で方向が決まらない場合は、右と下それぞれの必要移動量を比較して短い方を選ぶ。同量は下を優先する。この補完ルールは利用評価で確定する。左・上への押し出しや、同時の斜め移動は今回追加しない。

#### 7.3.2 移動量と連鎖衝突

現在のA・Bの外接矩形に対し、移動量を次のとおり求める。`gap` は既存の背景自動配置の間隔（現行設定 `SiblingGap`、初期値32px）を左右・上下に共通して使用し、マジックナンバーを追加しない。

```text
deltaX = A.right  + gap - B.left
deltaY = A.bottom + gap - B.top

右へ: Bの背景位置と全ノード・全接続線へ (deltaX, 0) を加算
下へ: Bの背景位置と全ノード・全接続線へ (0, deltaY) を加算
```

上式は内部重複がある組にだけ適用する。境界接触だけでは押し出さず、選んだ方向の必要量だけ移動する。1つの衝突では一方の軸だけを変えるが、別のツリーとの連鎖衝突で方向が変わった結果、最終的に両座標が変わることは許容する。

操作元の優先、保存位置のある背景を位置欠落背景より先に処理する規則、上端Y・背景ID数値順による決定的な優先順は維持する。位置欠落背景は従来どおり既存ツリーの下の空き位置へ初期配置し、今回の方向選択によって既定の新規背景位置を右側へ変更しない。

配置処理では、優先順で確定したツリー群を障害物として、次のツリーを配置する。同時に複数の障害物と衝突する場合は同じ優先順で1組ずつ処理し、移動後に全障害物との重複を再検証する。連鎖の各組で§7.3.1の方向判定を行い、最初の押し出し方向を全ツリーへ固定しない。

変更前の矩形は処理開始時の確定レイアウトから取得し、配置途中の候補で上書きしない。連鎖した2ツリーに変更前の矩形がない場合も暫定の必要移動量比較を用いる。X・Yを減らさず固定障害物の右端または下端を越えるため、一度解消した組へ逆戻りしない構造とする。再試行上限、有限座標と計算可能範囲の検証を維持し、失敗時は一括確定しない。

自動移動はツリー内部を再計算せず、キャッシュ済みの外接矩形を使う。文書変更・表示状態変更・影響した背景位置を一つの整合した結果として確定し、自動移動した背景位置も保存対象へ反映する。移動したツリーと影響範囲を利用者へ示す。失敗時に一部の背景位置だけ更新しない。解法の移動量・収束性は実装時に単体試験と実UI試験で確認する。

**実装状況:** 2026-10-28に `BackgroundPlacementService.ResolveCollisions` へ右・下の方向選択を実装し、下方のみの `ResolveBelow` を置き換えた。`AutoLayoutService` が `PreviousLayout` の背景別外接矩形を固定スナップショットとして渡し、優先順の障害物を1組ずつ解消して全障害物との重複を再検証する。方向不明時の最小移動量・同量なら下という補完は暫定ルールのまま実装した。有限・正の選択軸移動量、座標精度、再試行上限を検証し、失敗時は一括確定しない。

比較する変更前矩形は各 `Calculate` の開始時に参照する確定レイアウトである。ユーザー操作による予測配置を確定した後のDOMサイズ補正では、その予測確定結果が次の `PreviousLayout` になる。ユーザー操作開始前まで遡る別の矩形履歴は保持しない。配置処理中はこのスナップショットを候補位置で上書きしない。

`DocumentEditingSession` の一括確定、`TryMove` の重複拒否・開始位置復元、初期補完・読込補正の通知は維持する。新規背景の既定配置と形式3の保存構造も変更しない。今回の試験結果・実UI確認範囲は [QA_Q_sheet.md](QA_Q_sheet.md) を参照し、2026-10-27の下方のみの試験履歴は新方式の合格結果として流用しない。暫定補完ルールの利用評価はIssue #005で継続する。

### 7.4 個別ノードの手動配置

上位要求、下位要求、仕様の個別移動、兄弟の手動並べ替え、「自動配置へ戻す」操作は将来対応とする。背景位置を保存するために、子孫ごとの座標や自動／手動モードを追加しない。保存モデルは [DataModel.md](DataModel.md) を参照する。

## 8. 接続線設計

### 8.1 現行方式と確定事項

- 現行デモは HTML のノード要素と、絶対配置した1つの SVG 内の `<path>` を使用している。
- 親子接続線はベジェ曲線とする。
- UI 設計では親から子への方向を矢印で表示する。
- 関連する下位要求への接続線は初期版では表示しない。

### 8.2 描画規則

- 接続線の始点と終点は、親子ノードの境界上にある接続アンカーから求める。
- 親ノードの下辺中央を始点、子ノードの左辺中央を終点とする。2026-10-27のUI変更方針として、従来の親ノード右辺からの出力を下辺へ変更する。
- 背景から上位要求、上位要求から下位要求、下位要求から仕様に同じアンカー規則を適用する。
- 複数の子ノードへの接続線は、同じ親ノードの下辺中央から各子ノードの左辺中央へ描画する。保存モデルへ分岐用ノードを追加しない。
- 現行の3次ベジェ曲線を使用し、親の下辺から下方向へ出て、子の左側から右方向へ入るよう制御点を計算する。
- ノード座標またはサイズが変わった場合だけ、関係する接続線を再計算する。
- HTML ノードと SVG を共通のキャンバス変換下に置き、ズーム・パン時は個別の線形状を再計算しない。
- 背景ドラッグでは、対象ツリーの全ノード、始点、終点、制御点を同じ量だけ移動し、線形状を保つ。ツリー間の将来の関連リンクは両端の移動に応じて別途更新する。

接続位置は、ノード矩形の左上を `(x, y)`、幅を `width`、高さを `height` として次のとおり算出する。

```text
Start = (parent.x + parent.width / 2, parent.y + parent.height)
End   = (child.x, child.y + child.height / 2)
```

制御点の基本形は次のとおりとする。キャンバス座標は下方向をYの正方向とする。

```text
ControlPoint1 = (Start.x, Start.y + outgoingDistance)
ControlPoint2 = (End.x - incomingDistance, End.y)
outgoingDistance > 0
incomingDistance > 0
```

子ノードは必ず親の下へ配置されるため、`End.y > Start.y` となる。また、子の左辺を親幅の3/4へ置くため、`End.x > Start.x` だが `End.x < parent.right` となる。子が親の右端より右にあることを前提にしない。

曲がり量はこの始終点の距離とノード矩形に応じて調整する。制御点は下方向と右方向へ進む曲線を基本とし、初期設計では次の範囲に収める。

```text
0 < outgoingDistance <= End.y - Start.y
0 < incomingDistance <= End.x - Start.x
```

これにより、親から出た曲線を親の下側に保ち、子の左側から入れる。複数兄弟への線は親中心X座標と兄弟左辺の間を通す。曲線が先行サブツリーの本文・操作領域を横切らないよう確認する。具体的な距離係数は実装・UI評価で調整し、処理ごとに固定値を分散させない。

長文や理由の展開で高さが変わる場合は、最新の有効なノード矩形から下辺・左辺のアンカーと制御点を再計算する。キャンバスとSVGの描画範囲には曲線がノード矩形の外へ張り出す範囲も含め、下方向へ出る曲線が切れないようにする。接続アンカーと制御点は実行時の派生値とし、YAMLへ保存しない。

実装・回帰試験の確認項目:

- 単一の子と複数の子で、すべての線が親の下辺中央から出て子の左辺中央へ入ること。
- 4階層、複数背景、複数兄弟でも、子が親の下にあり、左辺が親幅の3/4の位置へ揃うこと。
- 先行兄弟に深い子孫がある場合も、次の兄弟がそのサブツリー全体の下にあり、左右の配置を崩さず接続できること。
- 長文、理由の展開・折りたたみ、DOM実測によるサイズ補正後も、線がノード境界へ追従すること。
- ズーム・パンでノードと線がずれず、曲線の張り出しが表示範囲で切れないこと。

現行実装では `ConnectionGeometry` が下辺・左辺のアンカーを算出し、`outgoingDistance = (End.y - Start.y) * ConnectionBendRatio`、`incomingDistance = (End.x - Start.x) * ConnectionBendRatio` とする。初期係数は `LayoutSettings.ConnectionBendRatio = 0.5` とした。縦・横それぞれの距離の半分を使うことで、制御点が始終点の範囲に収まり、下方向・右方向へ単調に進む曲線となる。子が親の右端より右にある条件は撤廃した。係数は `0 < ratio <= 1` とし、子が親の下側かつ下辺中央より右側にあることを検証する。`ConnectionClearance = 8px` は曲がり量には使わず、SVG線幅を切らないための最小描画余白として維持する。

曲線の微分の極値から実際の描画範囲を求める。子サブツリーの占有高さには曲線の下側張り出しを含め、その高さと兄弟間隔で次の兄弟を配置する。背景間の配置は§7.3に従う。キャンバスは全ノード・全曲線の範囲に余白を付ける。制御点そのものの矩形は過大な空白を作るため描画範囲として使用しない。

背景位置機能を追加する前の試験履歴として、2026-10-27に下方インデント配置のCore試験と実 `Home` を使ったChromium画面試験を実施した。Core全51件、JavaScript4件、7シナリオ42チェックが成功した。深い先行サブツリー、4階層、複数背景、長文・理由開閉、25〜200%ズーム・パンで、実DOM矩形との配置・接続整合とSVG内の描画範囲を確認した。画像・計測結果は `USDM_MindMap_Editor/artifacts/indented-layout/` に保存した。これは今回の背景ドラッグ・形式3・重複制御の合格結果ではなく、今回の実UI確認はSafariで別に記録する。検証履歴と残る可読性評価は [QA_Q_sheet.md](QA_Q_sheet.md) D-14を参照する。

### 8.3 大規模データ時の接続線

- DOM に表示していないノード間の接続線は描画しない。
- 表示対象集合には、可視ノードの祖先や接続関係を追うために必要な周辺ノードを含める。
- 両端ノードが描画対象に存在しない接続線は SVG 要素を生成しない。
- 将来の関連リンクは親子線と別レイヤーにし、表示切り替え可能な構造を推奨する。

接続線を SVG の単一要素へまとめるか、背景単位または表示領域単位で分割するかは、実測後に決定する。

## 9. ズーム・パン

### 9.1 操作

- キャンバスはドラッグによるパンを提供する。
- ホイールまたは UI 操作によるズームを提供する。
- ズーム範囲は最小25%、初期100%、最大200%とする。
- ホイールによるズームでは、ポインター位置をズーム中心とする。
- ズームリセットでは倍率を100%へ、パン位置を初期状態へ戻す。
- ステータスバーへズーム率を表示する。
- Fit All と Fit Selection は将来の補助操作とし、初期版では100%表示へのリセットを提供する。

### 9.2 実装方針

- ズームとパンは、HTML ノードと SVG 接続線を含む共通キャンバス要素への変換として適用する。
- 連続するポインター移動やホイール操作はブラウザ側で処理し、操作イベントごとの Interactive Server 往復を避ける。
- 操作終了時または必要な間隔で `CanvasState` と同期する。
- 最小倍率25%、初期倍率100%、最大倍率200%は設定値として一元管理し、UI と座標変換処理へ個別に埋め込まない。
- ポインター中心ズームでは、4.1節の座標変換に従ってパンオフセットを補正し、ズーム前に指していたキャンバス座標を同じビューポート位置へ維持する。
- ズーム倍率の1操作あたりの基本変化量は10%（倍率値 `0.10`）とし、設定値として管理する。
- 次の倍率は、現在倍率へ操作方向に応じて `0.10` を加減し、25%から200%の範囲へクランプする。

### 9.3 操作競合

初期版のパンはキャンバス余白から始まるドラッグで行う。ノード本体、下辺中央の子追加楕円、理由展開部、その他の操作部品を起点とする操作ではパンを開始しない。楕円への単一クリックを追加操作として受け付け、ドラッグとして判定された操作やポインターキャンセルでは追加しない。ドラッグ判定の移動許容値は、既存の画面上4 CSS pxを初期値として維持する。楕円の縦10pxとは別の設定であり、移動が4pxを超えた操作は楕円内へ戻っても追加しない。押下・リリースの両方で、最新のノード矩形から算出した楕円内にあることを確認する。

ポインター操作では、イベント対象が理由の文字や展開部であっても、子を追加可能な親ノードの楕円内かを理由操作より先に判定する。楕円内なら子追加として扱い、理由の既定クリック動作・展開イベントとキャンバス側への重複伝播を抑止する。一時的に理由を開閉してから元に戻す方法ではなく、理由状態の変更自体を発生させない。子追加ジェスチャーがドラッグやキャンセルとなった場合も、理由操作やパンへ切り替えない。

楕円外では理由操作を抑止せず、楕円の外接長方形を理由操作の遮蔽領域にしない。キーボード操作はフォーカスされた要素へ送る。背景本体からは§7のツリー全体ドラッグを開始し、上位要求・下位要求・仕様の本体からはパンやツリー移動を開始しない。判定は子追加楕円を優先し、操作部品、背景本体、キャンバス空白を区別する。背景移動後も古い楕円のホバーを残さない。

### 9.4 子追加領域の座標と描画

子追加領域は親ノードの下辺中央を中心とする楕円とする。縦の全長は画面上10 CSS pxで、下辺の上側5px・下側5pxに広がる。横の範囲は、親ノード左端から下辺長の1/4の位置から3/4の位置までとする。横幅は表示中のノード幅の1/2であり、下辺全幅ではない。縦寸法と横方向の比率はWeb UIのアプリケーション設定として管理し、縦寸法はズームで変化させない。

画面上での親ノード矩形を `viewRect` とすると、中心・半径・判定式は次のとおりとする。ポインター座標と矩形はビューポートの同じ座標系で扱う。

```text
centerX = viewRect.left + viewRect.width / 2
centerY = viewRect.bottom
radiusX = viewRect.width / 4
radiusY = 5 CSS px

((pointer.x - centerX) / radiusX)^2
  + ((pointer.y - centerY) / radiusY)^2 <= 1
```

ノード幅が画面上280pxの場合、楕円の横幅は140px、縦幅は10pxとなる。境界は判定対象に含め、外接長方形の四隅は含めない。見た目だけを楕円にして長方形全体をクリック可能とする実装にはしない。

ズーム変換を受けるノードの子要素として領域を描画する場合、キャンバス座標上の縦幅は `10 / zoom`、横幅はノード幅の1/2とする。パン・サイズ変更・理由開閉後も実際の下辺へ追従させる。判定は操作対象の親ノードの矩形から行い、ポインター移動のたびに全論理ノードを走査する構造にしない。

判定領域はノードの通常フロー外へ置き、領域自体やツールチップが予測サイズ・実測サイズ・サブツリー占有量を増加させない。外側へ出る5pxが親要素のクリッピングで失われないようにする。下辺の接続アンカーは元のノード矩形から算出する。SVG接続線と理由展開部より子追加の判定を優先できる描画順・イベント処理とし、楕円外のクリックは下層の理由操作などへ通常どおり届くようにする。

対象は背景・上位要求・下位要求に限る。クリックから入力確定までの流れ、ホバー・フォーカス表示、キャンセル・重複防止は [UI.md](UI.md) §8を正本とする。この領域とその状態はYAMLへ保存しない。

ヒット判定と強調表示の有効状態は分離する。ホバーやフォーカスの強調を消しても、楕円の判定範囲・理由操作より優先する処理・キーボードでの起動を無効にしない。Web層は、追加の起点となった入力方法、現在のホバー対象、ダイアログ開閉中か、終了後にホバーを再評価できるかを実行中だけ管理する。入力方法はダイアログ起動時に確定し、ダイアログ内の文字入力では上書きしない。

追加開始時と終了時にホバー対象・補助クラス・ツールチップ・カーソル状態を解除する。マウス起点では起点へDOMフォーカスを戻しても塗りつぶしを表示せず、新しいポインター操作で現在の矩形に対して楕円判定したときだけホバーを再開する。ポインターが動かない終了直後や、再配置前の座標に由来する `:hover` だけで強調を再開しない。キーボード起点では復帰したフォーカスを輪郭で示し、次のキーボード操作を継続できるようにする。

CSSの `:hover`、補助クラス、`:focus-visible` を無条件に同じ青い塗りつぶしへ結び付けず、起点の入力方法と有効な表示状態を反映する。フォーカス復帰を廃止したり、恒久的に強調を無効にしたりする対処は採用しない。輪郭も通常フロー外で描画し、ノード寸法・接続アンカーを変えない。利用者に見える状態の詳細は [UI.md](UI.md) §8を参照する。

2026-10-27に下辺全幅の4px帯を楕円へ変更した。`WebUiSettings.ChildAddHitHeight = 10`、`ChildAddWidthRatio = 0.5` とし、`ChildAddDragTolerance = 4` は独立に維持する。`Home` のフロー外オーバーレイは `clip-path: ellipse(...)` で四隅を除外し、`mindmapCanvas.js` の `inAdditionEllipse` は最新の画面上ノード矩形から本節の式で判定する。CSS幅にはノードの枠線を含め、表示幅の正確な1/2とする。

ポインターイベントはキャプチャ段階で対象ノードの楕円を確認し、理由の既定クリック動作が起きる前に抑止する。対象が理由のsummaryや本文でも同じ判定を使用する。CSSクリップ境界がキャンバスへヒットした場合だけ、近傍1点の `elementFromPoint` で親候補を取得して楕円式を再評価し、全ノード走査は行わない。ドラッグ・キャンセル後の互換クリックも抑止し、楕円外の理由操作とキーボードのフォーカス対象は維持する。既存ダイアログ、入力検証、重複防止、フォーカス復帰は変更していない。楕円仕様の試験結果は [QA_Q_sheet.md](QA_Q_sheet.md) D-14へ旧4px帯とは分けて記録した。

### 9.5 空白のダブルクリックによる背景追加

キャンバス空白の主ボタンダブルクリックで背景入力ダイアログを開く。ノード、子追加楕円、実際の接続線、操作部品、ダイアログ上は空白としない。SVGの透明な領域は空白として扱う。単一クリックでは追加せず、パンとして成立した操作に続くクリックから誤って起動しない。

ダブルクリック時の位置を§4.1でキャンバス座標へ変換し、新しい背景の左上位置の候補として保持する。ダイアログ中の画面変換で候補を取り直さない。入力保存時だけ背景を作成し、§7.3の重複解消後に背景位置を確定する。キャンセル・入力エラーでは文書、背景位置、採番結果を変更しない。重複するダイアログ起動も抑止する。

ツールバーの背景追加は維持し、指定位置がない場合は、外周余白を基準に既存ツリーの下の空き位置へ配置する。位置がない旧文書にも同じ初期配置規則を適用する。

### 9.6 上部メニューの折り畳みとビューポート

上部メニューの操作・表示は [UI.md](UI.md) §4.1を正本とする。折り畳みはツリーではなく画面の操作領域の切替であり、ノードやサブツリーの折り畳みとは区別する。

- ツールバーの高さを解放してキャンバスの表示領域を拡大し、再表示時は元の領域を確保する。画面高に追従し、固定の最小高さや非表示要素の余白が原因でステータスバーや切替ボタンを画面外へ追い出さない。
- 切替ボタンはキャンバス変換の外に置き、HTMLノード・SVG・ズーム・パンと一緒に移動・拡縮させない。ボタンとツールチップはツリーの占有範囲へ含めない。
- 背景配置位置、ノード・接続線の論理座標、ズーム倍率、パン値を変更しない。全体・局所レイアウト、サイズ全件測定、重複補正、Fit Allは切替だけでは実行しない。
- キャンバスのブラウザ上の原点・サイズが変わるため、表示切替後の最新のビューポート矩形を座標変換とヒット判定に使用する。論理原点は維持し、画面原点の変化を背景位置やパン値へ保存しない。将来のカリング判定も更新後の表示領域を使用する。
- パン値はキャンバス内を基準に維持するため、表示領域の原点が動いた分だけ画面上のノード位置が変わることはある。これはツリーの再配置ではない。
- 切替ボタン領域ではパン・背景追加・ツリー移動を開始しない。ドラッグ中やダイアログ表示中は切替を抑止し、古いビューポートを使ったジェスチャーを継続させない。
- 切替後は古い座標の子追加ホバー・ツールチップを解除し、次のポインター操作で最新の矩形から判定する。キーボードフォーカス表示は無効化しない。

2026-10-28の実装では、キャンバスDOMと変換を維持したままツールバーだけを非表示にし、画面高に追従するGridで解放した高さをキャンバスへ戻す。`mindmapCanvas.js` の `tryBeginToolbarToggle` で既存ジェスチャーとの競合を検証して切替中をロックし、表示状態に対応したDOMを `completeToolbarToggle` で確認してから解除する。完了時にはキャンバスの最新矩形を参照し、古い子追加ホバー・ツールチップを解除してフォーカスを復帰する。以後の座標変換とヒット判定もその時点のDOM矩形を参照し、ノードの全件測定やCoreへのレイアウト要求は追加しない。

## 10. 折り畳み・展開

本章はノード内の理由とサブツリーを対象とする。上部メニューの折り畳みは§9.6および [UI.md](UI.md) §4.1を参照する。

### 10.1 理由の表示

上位要求と下位要求の理由はデフォルトで折りたたむ。理由の展開はノードの表示サイズを変えるため、対象ノードを含む影響範囲のレイアウトと接続線を更新する。

### 10.2 サブツリー折り畳み

子ノードを隠すサブツリー折り畳みは、要求仕様書では将来拡張であり、現行コードにも実装されていない。

将来実装時の暫定方針は次のとおりである。

- 折り畳んだノードの子孫は DOM/SVG に描画しない。
- 折り畳みノードから非表示の子への接続線は描画しない。
- 折り畳みにより空いた領域は、対象サブツリーと祖先側の範囲で再配置する。
- 展開時は保存済み座標の復元ではなく、現在の文書構造から再配置する。
- 折り畳み状態を永続化するかは未決定とする。

サブツリー折り畳みは、同時描画ノード数を減らす大規模データ対策として有効である。

## 11. 大規模データ対応

### 11.1 保存可能件数と表示可能件数

設計資料上の ID 上限は各採番範囲あたり65535件である。ただし、この上限は保存形式上の採番範囲であり、同数のノードを快適に表示できることを保証しない。

v1.0 は、保存可能なデータ量と、実用的な操作性を評価・保証する描画規模を分離する。

| 指標 | v1.0 方針 |
|---|---|
| 保存・読み込み可能なデータ量の目標 | 10,000ノード以上 |
| 実用的な操作性の性能評価対象 | 2,000ノード |
| 2,000ノードを超える文書 | 使用を禁止しないが、v1.0 の性能保証対象外 |
| ID と保存形式の上限 | 各採番範囲65535件。性能保証値とは分離する |

2,000ノードは現時点の設計上の性能評価基準であり、正式な保証値は基準環境での性能試験後に確定する。10,000ノード以上の目標は YAML の保存・読み込みを対象とし、全件を同時描画して快適に操作できることを意味しない。

### 11.2 描画制御方針

- 論理レイアウトが保持する全ノードと、UI が DOM/SVG へ描画するノードの集合を分離する。
- レイアウト結果は全体または必要範囲について保持できるようにし、描画対象は別に選択する。
- ビューポートとその周辺余白に交差するノードを描画候補とする。周辺余白の具体値は性能試験と操作確認後に決定する。
- 検索結果、選択ノード、祖先ノードなど、操作継続に必要なノードは表示対象へ追加する。
- サブツリー折り畳みとビューポート外非描画を併用できる構造とする。
- ビューポートカリングは v1.0 の必須機能とはしない。2,000ノード性能試験が初期目標を満たさない場合は v1.0 の投入候補として再評価し、後付けを妨げない責務分離は v1.0 の設計へ含める。
- カリングを導入する場合、描画対象外のノードと、その両端が描画対象外である接続線は DOM/SVG を生成しない。サブツリー折り畳みは将来対応とする。

### 11.3 再計算範囲

- 初回読み込みは全体レイアウトを許容する。
- 追加、削除、表示サイズ変更では、影響サブツリーを優先して再計算する。
- 画面外ノードは予測サイズで計算し、レイアウト全体を DOM 測定へ依存させない。
- 全件再計算が必要な場合も、UI スレッドを長時間占有しない実行方法と進捗表示を将来検討する。

### 11.4 将来導入可能な最適化

- ビューポートカリング
- サブツリー折り畳み
- レイアウト結果のキャッシュ
- 背景またはサブツリー単位の部分レイアウト
- 接続線レイヤーの分割
- 描画更新のデバウンスまたはフレーム単位の集約
- Canvas または WebGL への描画方式変更

Canvas/WebGL 化は初期版の前提とせず、HTML ノードの編集性とアクセシビリティを優先する。実測で HTML + SVG の目標を満たせない場合の将来選択肢とする。

## 12. レイアウト処理の責務分担

### 12.1 責務

| 責務 | 配置 | 内容 |
|---|---|---|
| 文書構造 | Core | 背景、要求、仕様、親 ID、関連 ID を保持する |
| 予測サイズ計算 | Core | ノード内容、種類、既定幅、表示状態から DOM に依存しない予測サイズを計算する |
| レイアウト計算 | Core | 表示対象ツリーと有効サイズからキャンバス座標を計算する |
| ツリー配置・重複検証 | Core | 背景位置とツリー内相対座標を合成し、ツリー外接矩形による重複と自動移動を計算する |
| 接続線の幾何計算 | Core または専用計算クラス | ノード矩形から始点、終点、制御点を求める |
| SVG パス生成 | Web | 幾何情報を SVG の `path` 属性へ変換する |
| キャンバス状態 | Web | ズーム、パン、選択、ビューポートを管理する |
| ツリー移動ジェスチャー | Web / JavaScript 相互運用 | 開始位置・移動候補・キャンセルを管理し、対象のHTMLノードとSVG線だけを同量移動する |
| DOM 実測 | Web / JavaScript 相互運用 | 必要なノードだけを測定し、結果を Web 層へ返す |
| 実測サイズキャッシュ | Web | `NodeKey`、`LayoutRevision`、幅、理由展開状態とともに実測値を実行中だけ保持する |
| 描画対象選択 | Web | ビューポートと折り畳み状態から DOM/SVG 対象を選ぶ |
| UI 描画 | Web | HTML ノードと SVG 接続線を描画する |
| ビュー状態永続化 | Core / Application Service | 要求データと分離した背景配置位置、ズーム、パン、理由展開状態を YAML へ保存・復元する |
| 永続化 | Core | 文書データとビュー状態を区分した上で、決定的な YAML として保存する |

### 12.2 `ILayoutEngine`

レイアウト方式の差し替え、部分再計算、単体テストを可能にするため、Core 層に `ILayoutEngine` を置き、`AutoLayoutService` がこれを実装する構成を採用している。

必要な責務:

- 文書ツリー、背景配置位置、表示状態、予測値または有効な実測値、レイアウト設定を入力として受け取る。
- ノード ID ごとの矩形とキャンバス全体範囲を返す。
- 全体計算と、変更ノードを指定した部分計算を区別できる。
- Blazor コンポーネントや DOM API に依存しない。

レイアウト結果型、設定型、入力型、`ILayoutEngine`、`AutoLayoutService`、Web層からの呼び出しは実装済みである。今回、既存結果と変更背景IDを利用する背景単位の部分再計算を追加した。細粒度のサブツリー再計算、実測差分閾値、ノード単位Revision付き実測キャッシュは残課題である。確定操作の競合防止に使うSessionリビジョンは実装済みだが、この実測キャッシュのRevisionとは別である。

今回の背景配置は既存の入力・結果・状態管理を拡張して扱い、別のレイアウトエンジンや新規インターフェースは前提にしない。結果には背景別の占有範囲と所属ノード・接続線を対応付けられる情報が必要となる。ブラウザはドラッグ候補のプレビューをフレーム単位で更新し、確定時にCore側で再検証する。ポインター移動ごとのSignalR通信・DOM全件測定・全体レイアウトは行わない。

接続線の SVG 文字列まで Core 層で生成すると描画技術へ依存するため、Core は制御点まで、Web は SVG 変換を担当する構成を推奨する。

## 13. 永続化との関係

保存データの詳細は [DataModel.md](DataModel.md) を参照する。本書ではレイアウトとの関係だけを定義する。

| 状態 | 初期版の扱い | 区分 |
|---|---|---|
| 背景配置位置 | 背景の左上のキャンバス座標を `view.background_positions` に保存する | 確定 |
| 子孫ノード座標 | YAML に保存せず、背景位置と自動配置から再計算する | 確定 |
| 予測サイズ | ノード内容とアプリケーションの設定から再計算する | 実行時の派生情報 |
| DOM 実測サイズ | 必要なノードだけ取得し、YAML には保存しない | 実行時の派生情報 |
| 実測サイズキャッシュ | 現在の実行中だけ保持し、YAML には保存しない | 実行時の派生情報 |
| レイアウト設定値 | 初期版ではアプリケーション設定として管理し、文書 YAML には保存しない | 確定 |
| `LayoutRevision` | ノード内容の変更に応じて実行中だけ更新し、YAML には保存しない | 実行時の派生情報 |
| ズーム倍率 | 要求データと分離したプロジェクトのビュー状態として YAML に保存する | 確定 |
| パン位置 | 要求データと分離したプロジェクトのビュー状態として YAML に保存する | 確定 |
| 理由の展開状態 | 要求データと分離したノード単位のビュー状態として YAML に保存する | 確定 |
| `displayOrder` | 将来の手動並べ替え時だけ任意保存する。v1.0 では保存しない | 将来拡張 |
| サブツリー折り畳み状態 | 将来拡張。保存有無は未決定 | 未決定 |
| 個別ノードの自動／手動状態 | 個別の手動配置は将来拡張。背景移動のためのモード値は不要 | 将来拡張 |

ビュー状態の具体的な YAML 構造と互換性は [DataModel.md](DataModel.md) を正本とする。背景位置だけを保存し、子孫座標、予測サイズ、実測サイズ、`LayoutRevision`、サイズキャッシュ、ビューポート判定結果、未確定のドラッグ候補は保存しない。自動移動した背景も確定位置を保存する。背景削除時には対応する位置情報を削除する。

`view` 状態の永続化を初めて実装するリリースでは Application Version の Minor を上げる。YAML 形式は Application Version と分離して管理し、`view` 対応形式を形式バージョン2、`format_version` がない既存形式を形式バージョン1として扱う。具体的な Application Version はリリース計画で決定する。詳細は [DataModel.md](DataModel.md) を参照する。

背景配置位置の追加は意味のある保存形式変更のため、今回の対応形式を形式バージョン3としてCoreへ実装した。形式1・2と位置欠落のある形式3は、構造読込後に `DocumentEditingSession` が位置を補完し、必要な重複補正を行ってから確定する。形式2のズーム・パン・理由展開状態は維持する。Serializerは全背景の確定位置を持つ文書を形式3で出力し、不足時は検証エラーとする。Serializer内でレイアウトせず、未確定候補や実測値を保存しない。Application Versionは `0.1.0`、ファイル保存・読込UIは今回未接続である。

## 14. 性能目標

現行UIはサンプル文書をCoreのレイアウト結果から描画し、ズーム・パン、下辺からの子追加、ツールバー・空白ダブルクリックからの背景追加、背景ツリー全体移動を提供する。背景単位の部分再計算と重複制御を追加したが、大規模データでの追加時間や背景ドラッグを含む実UI性能は未測定である。削除、検索、本文編集は未実装である。

2026-08-10 に Apple M2 / 16GB 環境で行った Core の参考測定では、2,610ノードの YAML 保存中央値が約112ms、読み込み中央値が約52msであった。近似25,300ノードでは保存中央値が約105ms、読み込み中央値が約117msであった。これは一時的な測定であり、UI、SignalR、DOM、SVG、自動レイアウトを含まないため、受け入れ基準には使用しない。

初期性能評価環境は macOS、Apple Silicon M2、16GB メモリ、評価時点の Google Chrome 最新安定版とする。Chrome を v1.0 の一次性能基準とし、macOS と Chrome のバージョンを試験結果へ記録する。Safari 最新版は互換性と実動作の確認対象とする。Edge と Firefox は v1.0 の厳密な性能保証対象に含めない。

2,000ノードに対する設計上の初期性能目標は次のとおりとする。正式な v1.0 保証値は基準環境での性能試験後に確定する。

| 項目 | 設計上の初期目標 |
|---|---|
| 初回表示から操作可能まで | 2秒以内 |
| ノード追加 | 200ms以内 |
| ノード編集 | 200ms以内 |
| 局所レイアウト | 500ms以内 |
| YAML 保存 | 1秒以内 |
| ズーム・パン・背景のツリー全体ドラッグ | 60fpsを目標とし、2,000ノードで平均45fps以上、30fps未満が継続しないこと |
| メモリ | 読み込み、編集、保存の反復で使用量が増加し続けないこと |

10,000ノード以上では YAML の保存と読み込みが完了し、文書データが欠落しないことを確認する。10,000ノードの初回全件描画時間は v1.0 の性能保証対象に含めない。

FPS は設計上の初期目標であり、瞬間的な低下だけで不合格とはしない。操作中に30fps未満の状態が継続するかを重視し、正式な v1.0 保証値は実測後に確定する。背景のツリー全体ドラッグも同じ連続操作の評価対象とする。個別ノードの移動は対象外とする。

ブラウザメモリの絶対上限値は現時点で固定しない。アプリ起動直後、2,000ノード読み込み後、パン・ズーム・編集後、文書を閉じた後を測定する。読み込みとクローズ、編集と Undo / Redo、追加と削除を反復し、GC の変動を考慮しても使用量が一方向に増加し続けないことを確認する。検索、削除、YAML 読み込みの時間上限とメモリの絶対上限は測定結果から決定する。

### 14.1 性能試験項目

100、500、1,000、2,000ノードの測定用データを用意し、ノード数増加に対する変化を記録する。2,000ノードでは少なくとも次を測定する。

- 読み込みとクローズ、編集と Undo / Redo、追加と削除を反復したとき、メモリ使用量が一方向に増加し続けないこと

## 15. 実装上の禁止事項・注意事項

- Blazor コンポーネントへ複雑なレイアウト計算を直接埋め込まない。
- ノード1件の編集で、理由なく全ノードを再描画しない。
- 通常操作で全ノードを一括 DOM 測定しない。
- サイズ条件が変わっていないノードを繰り返し DOM 測定しない。
- 連続するズーム・パン操作を操作ごとに SignalR 送信しない。
- 全論理ノードが常に DOM/SVG に存在することを前提にしない。
- YAML の並び順を画面座標の代替として使用しない。
- YAML 保存形式へ一時的な描画キャッシュを保存しない。
- ID と座標、ID と兄弟表示順を混同しない。
- SVG 接続線と HTML ノードへ異なる座標変換を適用しない。
- ノードサイズを実測する場合、レイアウトと再描画が無限に繰り返されないよう収束条件を設ける。
- 関連リンクを親子リンクとして扱い、木構造の自動レイアウトへ混入させない。

- SVGのサイズはCoreが算出したキャンバス範囲を使用する構成へ変更済みである。

- ズーム倍率、パン位置、理由の展開状態に背景位置を加えた形式3のCore保存・復元を実装した。形式1は既定ビュー、形式2は既存ビューを引き継ぎ、背景位置はSession/Layoutで補完する。Serializer単独では位置を作らず、保存時は全背景の位置を必須とする。
- 下辺からの子追加、ツールバー・空白ダブルクリックからの背景追加を実装済み。`DocumentEditingSession` が候補文書上で `NodeCreationService` による検証・採番と `AutoLayoutService` による背景単位の再配置を実行する。既存の実測サイズとビュー状態を保持し、他ツリーは重複時だけ移動する。
- 子追加後の青い楕円の残留について、2026-10-27にSafari 27.0で修正前を確認した。文字入力後のEscape終了時、追加元はDOMフォーカスあり、`:hover=false`、`.is-hovered`なし、`:focus-visible=true`で、背景色が`rgb(37, 99, 235)`だった。実測できた残留経路はフォーカス復帰と`:focus-visible`の塗りつぶしの組み合わせである（アクセシビリティ経由の起動であり、マウス起点の全条件を再現したものではない）。`Home.razor.css`からネイティブのホバー・フォーカスによる塗りつぶしを分離し、有効な`.is-hovered`だけを青くする対策を実装した。`mindmapCanvas.js`で要求開始時の入力方法を固定し、送信中・表示中・終了時・非アクティブ化・変換・再配置の古いホバーとツールチップを解除する。新しいポインター移動で最新の楕円内を再検証するまで再強調しない。キーボード起点は独立した内側輪郭を復帰し、既存の`nodeInputDialog.js`によるDOMフォーカス復帰を維持する。Safariの修正後確認範囲と残項目は [QA_Q_sheet.md](QA_Q_sheet.md) D-14を参照する。
- 子追加は§9.3・9.4の縦10px・横1/4〜3/4の楕円へ変更済みである。見た目と判定式を一致させ、理由操作に対する子追加優先、楕円外の理由操作、ドラッグ・キャンセル、キーボード操作を単体・Chromium試験で確認した。旧4px帯の結果とは区別している。
- `displayOrder`、ビューポートカリング、FPS・メモリを含む2,000ノードの実UI性能試験は未実装である。編集、削除、検索、および画面からのYAMLファイル保存・読込も未実装である。
- 現行 YAML は `version`、`format_version`、`view` を固定順で出力する。対応可能な形式の旧 Application Version は `format_version` により読み込み、`version` の不一致だけでは拒否しない。
- `UsdmYamlReaderFactory` と形式1・2・3の専用Reader/DTO変換を実装した。構造検証と、Session/Layoutによる位置補完・サイズ依存の重複補正は分離する。
- `Home.razor` に `@rendermode InteractiveServer` を指定し、レイアウト結果をインタラクティブに描画する構成へ変更済みである。

### 17.2 資料間の確認事項

- [UI.md](UI.md) と [requirements_specification.md](requirements_specification.md) では、理由の展開・折りたたみを初期版、子ノードを隠すサブツリー折り畳みを将来対応として区別した。

- 初期版の手動配置は背景単位のツリー全体移動に限定する。従来の「手動移動なし」は今回この範囲で変更し、個別ノード移動は引き続き将来対応とする。

### 17.3 Issue #022との確認事項

- 保存・読み込み目標10,000ノード以上、性能評価対象2,000ノード、カリングの位置づけは [issues.md](issues.md) へ反映した。
