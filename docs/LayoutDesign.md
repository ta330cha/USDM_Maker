# USDM_MindMap_Editor レイアウト設計書

作成日: 2026-08-10

## 1. 目的

本書は、USDM_MindMap_Editor におけるノード配置、座標系、接続線、ズーム、パン、自動レイアウト、将来の手動配置、および大規模データ時の描画制御を定義する。

対象範囲は、USDM 文書の論理的な親子関係を、マインドマップとして配置・描画する処理である。要求内容、YAML スキーマ、画面上の文言や操作部品そのものは本書の主対象としない。

レイアウト方向、座標変換、配置間隔、サイズ計算、接続線計算、再レイアウト条件の詳細は本書を正本とし、他の設計書には各文書の責務に必要な要約だけを記載する。

### 1.1 他設計書との責務分担

| 文書 | 責務 |
|---|---|
| [requirements_specification.md](requirements_specification.md) | 実現する機能と要求を定義する |
| [architecture.md](architecture.md) | レイヤー構成、コンポーネント責務、依存関係を定義する |
| [DataModel.md](DataModel.md) | 保存対象データと内部データ構造を定義する |
| [UI.md](UI.md) | ユーザーに見える情報と操作結果を定義する |
| [issues.md](issues.md) | 未決定事項、決定内容、対応状態を管理する |
| 本書 | ノードと接続線を配置・描画・再配置する規則を定義する |

### 1.2 記載区分

本書では、各方針を次の区分で扱う。

| 区分 | 意味 |
|---|---|
| 確定 | 既存の要求仕様書または Issue で決定済み |
| 実装確認 | 現行コードで確認できる事実 |

| 将来拡張 | 初期版では実装しないが、将来の対応を妨げないよう考慮する事項 |

## 2. レイアウト設計の基本方針

### 2.1 確定事項

- USDM の背景、上位要求、下位要求、仕様の関係を、親子関係が視覚的に追えるマインドマップとして表示する。
- 初期版は自動整列かつ自動配置とする。
- 初期版ではノードの手動移動を提供しない。
- ノード座標は YAML に保存せず、読み込み時に再計算する。
- 親子接続線はベジェ曲線とする。
- 背景、上位要求、下位要求、仕様を左から右へ配置する。
- ノード間隔とキャンバス余白は一元管理するレイアウト設定値とする。
- ズーム範囲は25%から200%、初期値は100%とし、ポインター位置を中心にズームする。
- ノードサイズは予測値を基本とし、必要な場合だけ DOM 実測値で補正する。
- 通常の追加、編集、サイズ変更では、影響するサブツリーを局所的に再レイアウトする。
- v1.0 の複数背景と兄弟ノードは ID 昇順で安定して配置する。
- v1.0 の全ノードは、種類によらず共通の固定幅を使用する。
- DOM 実測値の有意差判定、サイズキャッシュ、ズーム操作量は設定値として管理する。
- ズーム倍率、パン位置、理由の展開状態は、要求データと分離したプロジェクトのビュー状態として保存する。

### 2.2 設計原則

- 要求本文の編集とレイアウト計算を分離し、文書データが描画方式へ依存しないようにする。
- レイアウト計算と UI 描画を分離し、同じ入力から再現可能な配置結果を得られるようにする。
- ノードの論理構造、レイアウト結果、ビューポート状態を別の状態として扱う。
- 初期版の自動配置を優先しつつ、将来の手動配置を追加できる構造を維持する。
- 保存可能なノード数と、同時に快適に描画できるノード数を分離して扱う。
- ノード数が増えた場合に、全件再計算と全件 DOM 描画だけに依存しない構造とする。

## 3. 論理レイアウト構造

### 3.1 基本親子構造

親子関係は次の木構造とする。

```text
背景
 ├─ 上位要求
 │   ├─ 下位要求
 │   │   ├─ 仕様
 │   │   └─ 仕様
 │   └─ 下位要求
 └─ 上位要求
```

確定済みの関係は次のとおりである。

- 1つの背景は複数の上位要求を持つことができる。
- 上位要求は必ず1つの背景に属する。
- 下位要求は必ず1つの上位要求に属する。
- 仕様は必ず1つの下位要求に属する。
- 上位要求、下位要求、仕様の複数親は認めない。
- 標準の親子レイアウトは木構造として計算する。

### 3.2 関連する下位要求

仕様の `related_requirement_ids` は、所属先以外の下位要求への横断参照である。親子関係、ID 採番、標準のツリーレイアウトには影響させない。

初期版では関連下位要求への接続線を表示しない。将来表示する場合は、親子接続線とは別の関連リンク層として扱い、ツリーの配置結果を変更しない方針とする。

## 4. 座標系

現行実装はCoreのレイアウト結果をHTMLノードとSVGへ共通の座標系で描画し、ブラウザ側の変換でズーム・パンを行う。ノード変更時の局所再レイアウトは編集操作実装時に接続する。

### 4.1 座標モデル

| 座標・状態 | 内容 | 管理責務 |
|---|---|---|
| キャンバス座標 | レイアウトエンジンが計算する論理座標。ズームやパンの影響を受けない | Core のレイアウト処理 |
| ノード座標 | キャンバス上のノード矩形の左上座標とサイズ | レイアウト結果 |
| ビューポート座標 | ブラウザ内の表示領域を基準とする座標 | Web UI |
| ズーム倍率 | キャンバス座標を表示倍率へ変換する係数 | `CanvasState` |
| パンオフセット | キャンバス原点をビューポート上で移動する量 | `CanvasState` |
| 接続線座標 | 親子ノード矩形から求める始点、終点、制御点 | 接続線計算処理 |

座標変換は次のとおりとする。

```text
viewportX = canvasX * zoom + panX
viewportY = canvasY * zoom + panY

canvasX = (viewportX - panX) / zoom
canvasY = (viewportY - panY) / zoom
```

HTML ノードと SVG 接続線は同じキャンバス座標系に置き、共通の変換を適用する。これにより、ズーム・パンだけでは個々の接続線座標を再計算しない構造を推奨する。

ポインター位置をズーム中心とする場合は、ズーム前にポインターが指すキャンバス座標を求め、ズーム後も同じビューポート位置になるようパンオフセットを更新する。

```text
canvasPoint = (pointerPosition - oldPan) / oldZoom
newPan = pointerPosition - canvasPoint * newZoom
```

### 4.2 座標の単位と精度

- キャンバス座標の単位は CSS pixel 相当を暫定案とする。
- 計算途中は小数を許可し、描画時に不要な丸めを行わない。
- ID はノード識別子であり、座標や表示順を表す値として使用しない。

## 5. ノード配置規則

### 5.1 配置方向

基本レイアウト方向は左から右とする。

```text
背景 → 上位要求 → 下位要求 → 仕様
```

- USDM の要求分解と具体化の流れを、左から右へ追えるようにする。
- 親ノードは子ノードより左側へ配置する。
- 同じ親を持つ子ノードは、親の右側で上下方向に並べる。
- 複数の背景は、互いのサブツリーが重ならないよう独立したルート領域へ配置する。
- 上下方向や放射型などの別レイアウトは初期版の対象外とする。

### 5.2 兄弟順序

v1.0 は、複数背景と同じ親を持つ兄弟ノードを ID 昇順で安定して表示する。各 ID セグメントを数値として比較し、例えば `999` を `1000` より前に配置する。

ユーザーによる手動並べ替えは将来対応とする。将来、表示順情報を導入した場合の優先順位は次のとおりとする。

1. 手動の表示順情報が存在するノードは、その順序を使用する。
2. 手動の表示順情報が存在しないノードは、ID 昇順を使用する。

v1.0 では表示順情報を YAML に保存せず、ID 昇順だけを使用する。将来の表示順項目の名称、型、採番方法は未決定である。

### 5.3 間隔と余白

ノード間隔とキャンバス余白は固定値を各処理へ分散させず、レイアウト設定値として一元管理する。初期値は次のとおりとする。

| 設定 | 初期値 |
|---|---:|
| 兄弟ノード間の最小間隔（複数背景を含む） | 32px |
| 親子階層間の間隔 | 96px |
| キャンバス外周余白 | 96px |

これらはアプリケーションのレイアウト設定値であり、初期版の文書 YAML には保存しない。将来の利用状況に応じて変更できる構造とする。ノード同士の重複回避を優先し、必要な場合は設定値より広い間隔を使用できる。

v1.0 は背景、上位要求、下位要求、仕様に共通の固定幅を使用し、可変幅は採用しない。ノード幅はレイアウト設定値として一元管理し、将来、種類別固定幅へ拡張できる構造を許容する。

正式な初期幅は UI 実測後に確定する。第一候補は `280px` とし、現行実装の `240px`、第一候補の `280px`、比較用の `320px` で表示を確認する。現行 CSS の最小高さ `110px` を正式仕様として維持するかも、同じ UI 確認で決定する。

### 5.4 ノード重複回避

レイアウト処理は次の順序で行う。

1. 表示対象ノードと親子構造を確定する。
2. 各ノードの有効な表示サイズを決定する。
3. 子孫を含むサブツリーの必要領域を末端から計算する。
4. ルートから順にノード座標を割り当てる。
5. ノード矩形の重複がないことを検証する。
6. 親子ノードの矩形から接続線を計算する。

### 5.5 ノードサイズ計算

ノードサイズは、予測サイズを基本とし、利用可能な DOM 実測サイズがある場合は実測値を優先するハイブリッド方式とする。

```text
ノード内容
  ↓
予測サイズ算出
  ↓
初期レイアウト
  ↓
DOM 描画
  ↓
必要なノードだけ実測
  ↓
差が無視できない場合だけ局所再レイアウト
```

有効サイズの優先順位は次のとおりとする。

```text
DOM 実測サイズ（有効なキャッシュがある場合）
  ↓ なければ
予測サイズ
```

### 5.6 予測サイズ

- DOM が存在しない初回レイアウトでも全ノードのサイズを算出できるようにする。
- ノード幅は全種別共通の固定幅とし、レイアウト設定の `NodeWidth` を使用する。
- ノード高さは、明示的な改行数、固定幅での折り返し行数、表示項目、余白、操作領域から予測する。
- 要求、理由、仕様の長さに応じて高さが変わることを許容する。

初期レイアウトでは次の式を使用する。

```text
ContentWidth = NodeWidth - (HorizontalPadding * 2)

EstimatedHeight =
    (VerticalPadding * 2)
  + IdAreaHeight
  + SectionGap
  + (TextLineCount * LineHeight)
  + ReasonAreaHeight
  + OtherVisibleFixedAreaHeight

ReasonAreaHeight =
  ReasonExpanded の場合:
    SectionGap + (ReasonLineCount * LineHeight)
  それ以外:
    0
```

本文と理由は明示的な改行ごとに分割し、各行について1行あたりの概算文字数から折り返し行数を求める。日本語中心の初期候補は1行16〜20文字とし、正式値は `240px`、`280px`、`320px` の幅比較と使用フォントの確認後に決定する。

| 設定 | 初期候補 |
|---|---:|
| 左右余白 | 16px |
| 上下余白 | 12px |
| 行高 | 22px |
| ID 領域高さ | 24px |
| セクション間隔 | 8px |
| 1行あたりの概算文字数 | 16〜20文字 |

常時表示する操作領域などがある場合は `OtherVisibleFixedAreaHeight` へ含める。その具体値と最小高さは UI 実測後に確定する。

### 5.7 DOM 実測とキャッシュ

DOM 実測は次の場合に限定する。

- 初回描画後に補正が必要なノード
- 本文を変更したノード
- 理由の展開など、サイズに影響する表示状態を変更したノード
- 予測値と実測値の差が無視できないノード

実測サイズは実行時キャッシュへ保持し、サイズ条件が変わらない限り再測定しない。全論理ノードの一括 DOM 測定を通常動作にはしない。

高さの実測差分閾値は次の式とし、設定値として管理する。

```text
Threshold = max(8px, EstimatedHeight * 10%)

abs(MeasuredHeight - EstimatedHeight) > Threshold
```

上記条件を満たす場合だけ差を有意と判断し、影響するサブツリーを局所再レイアウトする。閾値以下の差ではレイアウトを補正しない。幅は v1.0 で固定するため、実測幅が設定幅から外れた場合は設定または CSS の不整合として扱う。

キャッシュ識別情報は概念的に次の組とする。

```text
NodeKey
LayoutRevision
NodeWidth
ReasonExpanded
```

背景 ID と上位要求 ID は同じ値を取り得るため、`NodeKey` はノード種別と `NodeId` の組で一意にする。本文、理由、またはその他のサイズに影響する内容を変更した場合は、ノード単位の実行時 `LayoutRevision` を更新して旧キャッシュを無効化する。ノード幅または理由の展開状態が変わった場合も、キーの変化によって再測定する。

`LayoutRevision` とサイズキャッシュは実行時情報であり YAML へ保存しない。将来、フォントサイズやテーマが寸法へ影響する場合は、必要な値をキャッシュ識別情報へ追加できる構造とする。

入力中のキー操作ごとに再測定と全体レイアウトを行わず、編集確定または一定時間のデバウンス後に反映する。

## 6. 自動レイアウト

### 6.1 実行タイミング

| 操作 | 方針 | 区分 |
|---|---|---|
| 新規文書の初回表示 | 全体レイアウトを行う | 確定 |
| YAML 読み込み | 全体レイアウトを行う | 確定 |
| ノード追加 | 影響するサブツリーを再計算する | 確定 |
| ノード編集 | サイズが変わる場合に影響するサブツリーを再計算する | 確定 |
| ノード削除 | 影響するサブツリーを再計算する | 確定 |
| DOM 実測サイズの反映 | 予測値との差が閾値を超えた場合に影響するサブツリーを再計算する | 確定 |
| 理由の展開・折りたたみ | サイズが変わるノードと影響サブツリーを再計算する | 確定 |
| サブツリーの折り畳み・展開 | 対象サブツリーと祖先側の必要領域を再計算する | 将来拡張 |
| Fit All | レイアウト結果が古い場合は全体再計算を許可する | 将来拡張 |
| 明示的な全体自動整列 | 全体再計算を行う | 操作の提供時期は未決定 |
| 全体構造を大きく変更する操作 | 全体再計算を許可する | 確定 |

### 6.2 全体再計算と部分再計算

初回表示と YAML 読み込みでは全体再計算を許容する。通常のノード追加、編集、削除、実測サイズ変更では、変更ノード、その親、兄弟、および影響するサブツリーだけを再計算する。

部分再計算で重複を解消できない場合、背景単位のサブツリー再計算へ範囲を拡大し、それでも解消できない場合だけ全体再計算へフォールバックする。

```text
変更ノード
  ↓
直接の親・兄弟・子孫を再計算
  ↓ 解消不可
背景単位のサブツリーを再計算
  ↓ 解消不可
文書全体を再計算
```

### 6.3 再現性

同じ文書構造、ノードサイズ、レイアウト設定、折り畳み状態からは、同じ座標を生成する。ブラウザの描画順や列挙順に依存しない決定的な計算とし、Core 層の単体テスト対象にする。

## 7. 手動配置

初期版ではノードのドラッグ移動を提供せず、ノード座標も保存しない。したがって、初期版では自動配置が常に優先される。

手動配置は将来拡張であり、次の事項は未決定とする。

- ドラッグ移動後の座標を YAML に保存するか。
- 手動配置済みノードを自動配置対象から除外するか。
- 自動配置結果に手動オフセットだけを保持するか、絶対座標を保持するか。
- 「自動配置へ戻す」操作を提供するか。
- 親ノード移動時に子孫を追従させるか。
- 手動配置情報を文書共有情報とするか、ブラウザ個人設定とするか。

将来対応時は、文書上のノードデータへ直接座標責務を混在させず、[DataModel.md](DataModel.md) でレイアウト状態の保存モデルを別途定義する。

## 8. 接続線設計

### 8.1 現行方式と確定事項

- 現行デモは HTML のノード要素と、絶対配置した1つの SVG 内の `<path>` を使用している。
- 親子接続線はベジェ曲線とする。
- UI 設計では親から子への方向を矢印で表示する。
- 関連する下位要求への接続線は初期版では表示しない。

### 8.2 描画規則

- 接続線の始点と終点は、親子ノードの境界上にある接続アンカーから求める。
- 左から右への配置に合わせ、親ノードの右辺中央を始点、子ノードの左辺中央を終点とする。
- ベジェ曲線の制御点は始点、終点、配置方向、曲率設定から計算する。
- ノード座標またはサイズが変わった場合だけ、関係する接続線を再計算する。
- HTML ノードと SVG を共通のキャンバス変換下に置き、ズーム・パン時は個別の線形状を再計算しない。

### 8.3 大規模データ時の接続線

- DOM に表示していないノード間の接続線は描画しない。
- 表示対象集合には、可視ノードの祖先や接続関係を追うために必要な周辺ノードを含める。
- 両端ノードが描画対象に存在しない接続線は SVG 要素を生成しない。
- 将来の関連リンクは親子線と別レイヤーにし、表示切り替え可能な構造を推奨する。

接続線を SVG の単一要素へまとめるか、背景単位または表示領域単位で分割するかは、実測後に決定する。

## 9. ズーム・パン

### 9.1 操作

- キャンバスはドラッグによるパンを提供する。
- ホイールまたは UI 操作によるズームを提供する。
- ズーム範囲は最小25%、初期100%、最大200%とする。
- ホイールによるズームでは、ポインター位置をズーム中心とする。
- ズームリセットでは倍率を100%へ、パン位置を初期状態へ戻す。
- ステータスバーへズーム率を表示する。
- Fit All と Fit Selection は将来の補助操作とし、初期版では100%表示へのリセットを提供する。

### 9.2 実装方針

- ズームとパンは、HTML ノードと SVG 接続線を含む共通キャンバス要素への変換として適用する。
- 連続するポインター移動やホイール操作はブラウザ側で処理し、操作イベントごとの Interactive Server 往復を避ける。
- 操作終了時または必要な間隔で `CanvasState` と同期する。
- 最小倍率25%、初期倍率100%、最大倍率200%は設定値として一元管理し、UI と座標変換処理へ個別に埋め込まない。
- ポインター中心ズームでは、4.1節の座標変換に従ってパンオフセットを補正し、ズーム前に指していたキャンバス座標を同じビューポート位置へ維持する。
- ズーム倍率の1操作あたりの基本変化量は10%（倍率値 `0.10`）とし、設定値として管理する。
- 次の倍率は、現在倍率へ操作方向に応じて `0.10` を加減し、25%から200%の範囲へクランプする。

### 9.3 操作競合

初期版にはノードドラッグがないため、ドラッグはキャンバスのパンとして扱える。将来ノードドラッグを追加する場合は、ノード上のドラッグを移動、キャンバス余白上のドラッグをパンとして区別する案を検討する。

## 10. 折り畳み・展開

### 10.1 理由の表示

上位要求と下位要求の理由はデフォルトで折りたたむ。理由の展開はノードの表示サイズを変えるため、対象ノードを含む影響範囲のレイアウトと接続線を更新する。

### 10.2 サブツリー折り畳み

子ノードを隠すサブツリー折り畳みは、要求仕様書では将来拡張であり、現行コードにも実装されていない。

将来実装時の暫定方針は次のとおりである。

- 折り畳んだノードの子孫は DOM/SVG に描画しない。
- 折り畳みノードから非表示の子への接続線は描画しない。
- 折り畳みにより空いた領域は、対象サブツリーと祖先側の範囲で再配置する。
- 展開時は保存済み座標の復元ではなく、現在の文書構造から再配置する。
- 折り畳み状態を永続化するかは未決定とする。

サブツリー折り畳みは、同時描画ノード数を減らす大規模データ対策として有効である。

## 11. 大規模データ対応

### 11.1 保存可能件数と表示可能件数

設計資料上の ID 上限は各採番範囲あたり65535件である。ただし、この上限は保存形式上の採番範囲であり、同数のノードを快適に表示できることを保証しない。

v1.0 は、保存可能なデータ量と、実用的な操作性を評価・保証する描画規模を分離する。

| 指標 | v1.0 方針 |
|---|---|
| 保存・読み込み可能なデータ量の目標 | 10,000ノード以上 |
| 実用的な操作性の性能評価対象 | 2,000ノード |
| 2,000ノードを超える文書 | 使用を禁止しないが、v1.0 の性能保証対象外 |
| ID と保存形式の上限 | 各採番範囲65535件。性能保証値とは分離する |

2,000ノードは現時点の設計上の性能評価基準であり、正式な保証値は基準環境での性能試験後に確定する。10,000ノード以上の目標は YAML の保存・読み込みを対象とし、全件を同時描画して快適に操作できることを意味しない。

### 11.2 描画制御方針

- 論理レイアウトが保持する全ノードと、UI が DOM/SVG へ描画するノードの集合を分離する。
- レイアウト結果は全体または必要範囲について保持できるようにし、描画対象は別に選択する。
- ビューポートとその周辺余白に交差するノードを描画候補とする。
- 検索結果、選択ノード、祖先ノードなど、操作継続に必要なノードは表示対象へ追加する。
- サブツリー折り畳みとビューポート外非描画を併用できる構造とする。
- ビューポートカリングは性能試験で必要性が確認された場合に導入する。v1.0 の必須機能とはしないが、後付けを妨げない責務分離は v1.0 の設計へ含める。
- カリングを導入する場合、描画対象外のノードと、その両端が描画対象外である接続線は DOM/SVG を生成しない。サブツリー折り畳みは将来対応とする。

### 11.3 再計算範囲

- 初回読み込みは全体レイアウトを許容する。
- 追加、削除、表示サイズ変更では、影響サブツリーを優先して再計算する。
- 画面外ノードは予測サイズで計算し、レイアウト全体を DOM 測定へ依存させない。
- 全件再計算が必要な場合も、UI スレッドを長時間占有しない実行方法と進捗表示を将来検討する。

### 11.4 将来導入可能な最適化

- ビューポートカリング
- サブツリー折り畳み
- レイアウト結果のキャッシュ
- 背景またはサブツリー単位の部分レイアウト
- 接続線レイヤーの分割
- 描画更新のデバウンスまたはフレーム単位の集約
- Canvas または WebGL への描画方式変更

Canvas/WebGL 化は初期版の前提とせず、HTML ノードの編集性とアクセシビリティを優先する。実測で HTML + SVG の目標を満たせない場合の将来選択肢とする。

## 12. レイアウト処理の責務分担

### 12.1 責務

| 責務 | 配置 | 内容 |
|---|---|---|
| 文書構造 | Core | 背景、要求、仕様、親 ID、関連 ID を保持する |
| 予測サイズ計算 | Core | ノード内容、種類、既定幅、表示状態から DOM に依存しない予測サイズを計算する |
| レイアウト計算 | Core | 表示対象ツリーと有効サイズからキャンバス座標を計算する |
| 接続線の幾何計算 | Core または専用計算クラス | ノード矩形から始点、終点、制御点を求める |
| SVG パス生成 | Web | 幾何情報を SVG の `path` 属性へ変換する |
| キャンバス状態 | Web | ズーム、パン、選択、ビューポートを管理する |
| DOM 実測 | Web / JavaScript 相互運用 | 必要なノードだけを測定し、結果を Web 層へ返す |
| 実測サイズキャッシュ | Web | `NodeKey`、`LayoutRevision`、幅、理由展開状態とともに実測値を実行中だけ保持する |
| 描画対象選択 | Web | ビューポートと折り畳み状態から DOM/SVG 対象を選ぶ |
| UI 描画 | Web | HTML ノードと SVG 接続線を描画する |
| ビュー状態永続化 | Core / Application Service | 要求データと分離したズーム、パン、理由展開状態を YAML へ保存・復元する |
| 永続化 | Core | 文書データとビュー状態を区分した上で、決定的な YAML として保存する |

### 12.2 `ILayoutEngine`

レイアウト方式の差し替え、部分再計算、単体テストを可能にするため、Core 層に `ILayoutEngine` を置き、`AutoLayoutService` がこれを実装する構成を採用している。

必要な責務:

- 文書ツリー、表示状態、予測値または有効な実測値、レイアウト設定を入力として受け取る。
- ノード ID ごとの矩形とキャンバス全体範囲を返す。
- 全体計算と、変更ノードを指定した部分計算を区別できる。
- Blazor コンポーネントや DOM API に依存しない。

レイアウト結果型、設定型、入力型、`ILayoutEngine`、`AutoLayoutService`、Web 層からの呼び出しは初期実装済みである。ノード変更時の局所再計算、差分閾値、Revision 付き実測キャッシュは編集操作実装時に接続する。

接続線の SVG 文字列まで Core 層で生成すると描画技術へ依存するため、Core は制御点まで、Web は SVG 変換を担当する構成を推奨する。

## 13. 永続化との関係

保存データの詳細は [DataModel.md](DataModel.md) を参照する。本書ではレイアウトとの関係だけを定義する。

| 状態 | 初期版の扱い | 区分 |
|---|---|---|
| ノード座標 | YAML に保存せず、読み込み時に再計算する | 確定 |
| 予測サイズ | ノード内容とアプリケーションの設定から再計算する | 実行時の派生情報 |
| DOM 実測サイズ | 必要なノードだけ取得し、YAML には保存しない | 実行時の派生情報 |
| 実測サイズキャッシュ | 現在の実行中だけ保持し、YAML には保存しない | 実行時の派生情報 |
| レイアウト設定値 | 初期版ではアプリケーション設定として管理し、文書 YAML には保存しない | 確定 |
| `LayoutRevision` | ノード内容の変更に応じて実行中だけ更新し、YAML には保存しない | 実行時の派生情報 |
| ズーム倍率 | 要求データと分離したプロジェクトのビュー状態として YAML に保存する | 確定 |
| パン位置 | 要求データと分離したプロジェクトのビュー状態として YAML に保存する | 確定 |
| 理由の展開状態 | 要求データと分離したノード単位のビュー状態として YAML に保存する | 確定 |
| サブツリー折り畳み状態 | 将来拡張。保存有無は未決定 | 未決定 |
| 自動／手動レイアウト状態 | 手動配置自体が将来拡張 | 未決定 |

ビュー状態の具体的な YAML 構造と互換性は [DataModel.md](DataModel.md) を正本とする。ノード座標、予測サイズ、実測サイズ、`LayoutRevision`、サイズキャッシュ、ビューポート判定結果は保存しない。

## 14. 性能目標

現行 UI はサンプル文書をCoreのレイアウト結果から描画し、ズーム・パンを提供する段階である。追加、削除、検索、編集操作と実UI性能は未測定である。

2026-08-10 に Apple M2 / 16GB 環境で行った Core の参考測定では、2,610ノードの YAML 保存中央値が約112ms、読み込み中央値が約52msであった。近似25,300ノードでは保存中央値が約105ms、読み込み中央値が約117msであった。これは一時的な測定であり、UI、SignalR、DOM、SVG、自動レイアウトを含まないため、受け入れ基準には使用しない。

初期性能評価環境は、開発環境資料と既存測定に合わせて macOS、Apple Silicon M2、16GB メモリとする。macOS とブラウザのバージョンは試験結果へ記録する。UI 確認対象は Safari と Chrome だが、どちらを正式な性能保証ブラウザとするか、または両方を対象とするかは未決定である。

2,000ノードに対する設計上の初期性能目標は次のとおりとする。正式な v1.0 保証値は基準環境での性能試験後に確定する。

| 項目 | 設計上の初期目標 |
|---|---|
| 初回表示から操作可能まで | 2秒以内 |
| ノード追加 | 200ms以内 |
| ノード編集 | 200ms以内 |
| 局所レイアウト | 500ms以内 |
| YAML 保存 | 1秒以内 |
| ズーム・パン | 明確な遅延や引っ掛かりを感じないこと |
| メモリ | 読み込み、編集、保存の反復で使用量が増加し続けないこと |

10,000ノード以上では YAML の保存と読み込みが完了し、文書データが欠落しないことを確認する。10,000ノードの初回全件描画時間は v1.0 の性能保証対象に含めない。

FPS の数値保証、検索・削除・YAML 読み込みの時間上限、ブラウザとサーバーそれぞれのメモリ上限は未決定とする。ノード移動は v1.0 の対象外であり、将来実装時に性能目標を定める。

### 14.1 性能試験項目

100、500、1,000、2,000ノードの測定用データを用意し、ノード数増加に対する変化を記録する。2,000ノードでは少なくとも次を測定する。

- YAML 選択からノード表示と主要操作が可能になるまでの初回表示時間
- ノード追加操作の開始から描画と必要な再配置が完了するまでの時間
- ノード編集確定から描画と必要な再配置が完了するまでの時間
- 影響サブツリーだけを対象にしたレイアウト計算時間と、影響外ノードが不必要に移動していないこと
- YAML 保存操作からダウンロード生成までの時間
- 連続するパンとズームの引っ掛かり、入力追従性、および SignalR 通信回数
- 初回表示後、追加・編集反復後、保存後のブラウザとサーバーのメモリ使用量
- DOM/SVG 要素数、DOM 実測対象数、全体再レイアウト回数、局所再レイアウト回数

10,000ノード以上のデータでは、YAML 保存、読み込み、再保存が完了し、ノード、親子関係、関連要求、ビュー状態が欠落しないことを確認する。ブラウザ名とバージョン、macOS バージョン、測定方法、測定データの階層別件数と文字量を結果へ記録する。

## 15. 実装上の禁止事項・注意事項

- Blazor コンポーネントへ複雑なレイアウト計算を直接埋め込まない。
- ノード1件の編集で、理由なく全ノードを再描画しない。
- 通常操作で全ノードを一括 DOM 測定しない。
- サイズ条件が変わっていないノードを繰り返し DOM 測定しない。
- 連続するズーム・パン操作を操作ごとに SignalR 送信しない。
- 全論理ノードが常に DOM/SVG に存在することを前提にしない。
- YAML の並び順を画面座標の代替として使用しない。
- YAML 保存形式へ一時的な描画キャッシュを保存しない。
- ID と座標、ID と兄弟表示順を混同しない。
- SVG 接続線と HTML ノードへ異なる座標変換を適用しない。
- ノードサイズを実測する場合、レイアウトと再描画が無限に繰り返されないよう収束条件を設ける。
- 関連リンクを親子リンクとして扱い、木構造の自動レイアウトへ混入させない。

### 17.4 判断材料不足

- ノード本文の最大長。
- ノード幅、1行あたりの概算文字数、操作領域高さ、最小高さの UI 実測結果。
- レスポンシブ表示時にレイアウトを再計算するか、表示変換だけで対応するか。
- ノード検索結果へ移動するとき、折り畳み解除や自動ズームを行うか。
- 可視領域外の接続関係をどの程度画面上に示すか。
- レイアウト処理を同期実行するか、キャンセル可能な非同期処理とするか。
