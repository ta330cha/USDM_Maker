# USDM_MindMap_Editor アーキテクチャ設計書

作成日: 2026-07-15

## 1. 目的

本書は、USDM_MindMap_Editor のアプリケーション構成、主要コンポーネント、責務分担、処理方針を定義する。

## 2. 技術前提

- 実装言語: C#
- Web フレームワーク: ASP.NET Core + Blazor Web App
- 対象 .NET: .NET 10
- UI: Blazor コンポーネント、HTML、CSS、SVG
- 保存形式: YAML
- 実行方式: ローカル Web アプリケーション
- 開発 OS: macOS / Apple Silicon

## 3. ソリューション構成

推奨構成:

```text
USDM_Maker/ (ワークスペースの最上位フォルダ)
  USDM_MindMap_Editor.sln
  global.json
  src/
    USDM_MindMap_Editor.Core/
    USDM_MindMap_Editor.Web/
  tests/
    USDM_MindMap_Editor.Core.Tests/
  docs/
```

| プロジェクト | 役割 |
|---|---|
| `USDM_MindMap_Editor.Core` | USDM データモデル、ID 採番、YAML 入出力、検証、レイアウト計算 |
| `USDM_MindMap_Editor.Web` | Blazor Web App、画面、ユーザー操作、ファイル入出力 UI |
| `USDM_MindMap_Editor.Core.Tests` | Core 層の単体テスト |

## 4. レイヤー構成

```text
Web UI
  ↓
Application Service
  ↓
Domain Model
  ↓
Persistence
```

### Web UI

Blazor コンポーネントで画面を構成する。

責務:

- キャンバス表示
- ノード表示
- 入力ダイアログ表示
- ユーザー操作の受付
- ズーム、パン、理由展開状態の管理
- YAML ファイルの読み込み、保存操作

### Application Service

UI とドメイン処理の間をつなぐ。

責務:

- ノード追加、編集、削除のユースケース実行
- コピー、ペースト、検索のユースケース実行
- ID 採番サービスの呼び出し
- YAML 入出力サービスの呼び出し
- 実行中のキャンバス状態と永続化するビュー状態の相互変換
- USDM 表エクスポートの実行
- 検証結果の UI 返却

### Domain Model

USDM の構造を表現する。

責務:

- 背景
- 上位要求
- 下位要求
- 仕様
- 単一親の親子関係
- 仕様から関連下位要求への参照
- ID ルール
- 自動レイアウトの対象となるツリー構造

要求データとプロジェクトのビュー状態は同じ YAML 文書に保存するが、ドメイン上の責務は分離する。ビュー状態は要求の親子関係や検証結果へ影響させない。

### Persistence

YAML 形式で保存、読み込みを行う。

責務:

- YAML へのシリアライズ
- YAML からのデシリアライズ
- 要求データとビュー状態の決定的な保存・復元
- ブラウザのダウンロードとしての YAML 出力
- 保存時のソフトウェアバージョンの記録
- ソフトウェアバージョンと YAML 形式バージョンの分離
- `format_version` に応じた読み込みと現在の内部モデルへの変換

## 6. データフロー

### 新規ノード追加

```text
ユーザー操作
  ↓
Blazor コンポーネント
  ↓
Application Service
  ↓
IdGenerator
  ↓
UsdmDocument 更新
  ↓
AutoLayoutService
  ↓
画面再描画
```

### YAML 保存

```text
保存操作
  ↓
DocumentValidator
  ↓
要求データとビュー状態を保存モデルへ統合
  ↓
UsdmYamlSerializer
  ↓
ブラウザのダウンロード
```

### YAML 読み込み

```text
ファイル選択
  ↓
UsdmYamlReaderFactory
  ↓
IUsdmVersionedReader
  ↓
UsdmDocumentMigrator
  ↓
DocumentValidator
  ↓
AutoLayoutService
  ↓
保存されたビュー状態を CanvasState と理由表示状態へ復元
  ↓
画面表示
```

`format_version` がない旧 YAML は形式バージョン1として扱う。旧 YAML にビュー状態が存在しない場合は、ズーム100%、パン位置 `(0, 0)`、理由を折りたたんだ初期状態を使用する。

### ノードサイズ補正

```text
Core で予測サイズを算出
  ↓
予測サイズでレイアウト計算
  ↓
Web UI でノード描画
  ↓
必要なノードだけ JavaScript 相互運用で DOM 実測
  ↓
Web 層の実測サイズキャッシュを更新
  ↓
差が閾値を超えた場合だけ影響サブツリーを再計算
```

Core 層は DOM API に依存しない。Web 層は、ノード種別と ID からなる一意な `NodeKey`、実行時 `LayoutRevision`、ノード幅、理由展開状態を識別情報として実測サイズをキャッシュする。本文や理由などのサイズ条件が変化した場合は `LayoutRevision` を更新し、有効な実測値がなければ Core 層の予測値を使用する。`LayoutRevision` とキャッシュは永続化しない。

### USDM 表エクスポート

```text
エクスポートメニュー
  ↓
DocumentValidator
  ↓
ExportWarningService
  ↓
UsdmTableExporter
  ↓
ブラウザのダウンロード
```

## 7. ID 採番方針

要求仕様書の定義に従い、初期値は以下とする。

| 種別 | 形式 | 上限 |
|---|---|---|
| 背景 | `001`〜`65535` | 65535件 |
| 上位要求 | `001`〜`65535` | 65535件 |
| 下位要求 | `001-001` | 親ごと65535件 |
| 仕様 | `001-001-001` | 親ごと65535件 |

ID の各セグメントは `001`〜`999` を3桁ゼロ埋め、`1000`〜`65535` をそのまま表記する。背景 ID は `001` から開始し、`000` は使用しない。初期版の上限は各採番範囲あたり65535件とする。

## 8. 親子関係と関連要求の方針

- 背景は最上位ノードとし、上位要求は必ず1つの背景に属する。
- 下位要求は必ず1つの上位要求に属する。
- 仕様は必ず1つの下位要求に属する。
- 上位要求、下位要求、仕様の複数親は認めない。
- 仕様に関連する下位要求がある場合は、`related_requirement_ids` に ID を保存する。
- 関連下位要求は参照情報であり、仕様の親子関係、ID 採番、標準のツリー接続線を変更しない。

`DocumentValidator` は、親 ID の存在、親の種別、ID 接頭辞、関連下位要求 ID の存在と重複を検証する。理由の未入力は YAML 保存時のエラーにせず、エクスポート時に `ExportWarningService` が警告として扱う。

## 9. レイアウト方針

初期版は左から右への自動整列かつ自動配置とする。ノードの追加、編集、削除、YAML 読み込み後に `AutoLayoutService` が必要な位置を再計算する。

複数背景と同じ親を持つ兄弟ノードは、ID の各セグメントを数値として比較した昇順で Core 層が安定して並べる。将来、手動表示順を追加する場合は Core 層が `displayOrder`（概念上 `int?`）の設定済みノードを値の昇順、同値を ID 昇順で並べ、その後に未設定ノードを ID 昇順で並べる。v1.0 は `displayOrder` を保持せず、手動並べ替えをしていないノードへ不要な値を保存しない。

ノード位置は YAML に保存せず、ユーザーによる手動移動も提供しない。手動配置と座標保存は将来拡張とする。

レイアウト計算と予測サイズ計算は Core 層、キャンバス状態、実測サイズキャッシュ、描画対象の選択は Web 層の責務とする。要求データ、レイアウト結果、実行時キャッシュ、永続化するビュー状態を分離し、YAML 保存処理は実行時のレイアウト結果や DOM 情報へ依存させない。

ノードサイズは予測値を基本とし、有効な DOM 実測値がある場合だけ実測値を優先する。DOM 実測は Web 層から JavaScript 相互運用を介して必要なノードだけに行い、結果を実行中のキャッシュへ保持する。全ノードを通常動作のたびに測定せず、予測値との差が設定された閾値を超えた場合だけ局所再レイアウトを要求する。

YAML 読み込み、新規文書の初回配置、明示的な全体自動整列、および全体構造を大きく変更する操作では全体レイアウトを許可する。通常のノード追加、編集、削除、表示サイズ変更では、影響するサブツリーを再計算し、重複を解消できない場合に背景単位、文書全体へ範囲を広げる。

兄弟間隔、階層間隔、キャンバス余白、共通固定ノード幅、サイズ予測パラメーター、実測差分閾値、ズーム範囲、10%のズーム操作量は各処理へ埋め込まず、一元管理するアプリケーション設定として Core と Web の必要箇所へ渡す。初期版では文書 YAML に含めない。

レイアウト方式の差し替えと単体テストを可能にするため、`AutoLayoutService` が Core 層の `ILayoutEngine` を利用する構成を採用する。初期実装では左から右の自動配置、予測サイズ、実測サイズの反映、親子接続線の幾何計算までを提供し、ノード変更時の局所再計算は編集操作とともに拡張する。

詳細な配置規則、座標系、再計算範囲は [LayoutDesign.md](LayoutDesign.md) を参照する。

## 10. 描画方針

マインドマップのノードと接続線は Blazor + SVG で描画し、接続線はベジェ曲線とする。

理由:

- ノード間接続線を描画しやすい
- ズーム、パンとの相性がよい
- 親子関係をベジェ曲線で視覚的に追いやすい
- Canvas より DOM 要素として扱いやすく、初期実装の保守性が高い

ノード本体は HTML 要素として重ねる方式、または SVG 内に描画する方式のどちらも可能とする。入力やダイアログとの相性を考えると、初期実装では HTML ノード + SVG 接続線を推奨する。

現行実装は HTML ノード + SVG 接続線を使用し、Coreのレイアウト結果からデータ駆動で描画する。

親子接続線の幾何計算は、親ノードの下辺中央と子ノードの左辺中央をアンカーとし、下方向へ出て子の左側から入る3次ベジェ曲線の制御点をCore側で算出する。Web層は計算結果をSVGパスへ変換する。ノード矩形の変更時にアンカーと制御点を更新し、描画範囲は曲線の張り出しも考慮する。詳細は [LayoutDesign.md](LayoutDesign.md) を参照する。この下辺出力の規則は設計変更であり、現行実装への反映は後続作業とする。

大規模データ対応では、文書が保持する全ノード、Core が保持する論理座標、Web 層が実際に描画するノードを分離する。Web 層の描画対象選択を介して、ビューポートと一定の周辺余白に交差するノードだけを描画する方式、サブツリー折り畳み、接続線の描画対象制御を後から導入できるようにする。周辺余白値は未決定とする。ビューポートカリングは v1.0 の必須機能とはせず、2,000ノードの性能試験が目標未達の場合に v1.0 の投入候補として再評価する。

ズーム・パンは HTML ノードと SVG 接続線を含む共通キャンバス変換としてブラウザ側で処理し、連続操作を Interactive Server の通信ごとに処理しない。ズーム範囲は25%から200%、初期値は100%、基本操作量は10%とし、設定値として管理する。ポインター中心ズームでは、ズーム前後でポインターが指すキャンバス座標を同じビューポート位置へ維持するようパンオフセットを補正する。

ブラウザ側は連続的な座標変換と限定的な DOM 実測を担当し、Blazor 側は確定したキャンバス状態、実測結果、レイアウト再計算要求を扱う。保存時は `CanvasState` と理由展開状態を要求データと分離したビュー状態へ変換し、読み込み時に復元する。ブラウザ側処理と `CanvasState` を同期する具体的な頻度は実装時に決定する。描画方式と座標変換の詳細は [LayoutDesign.md](LayoutDesign.md) を参照する。

## 11. エラーハンドリング

想定する検証エラー:

- YAML の構文エラー
- 未対応の YAML 形式バージョン
- 旧ファイル形式からの変換エラー
- 必須項目不足
- ID 重複
- ID 形式不正
- 親参照の不整合
- 複数または未設定の親
- 関連下位要求 ID の参照先不正
- 上限件数超過

エクスポート時の理由未入力は警告であり、YAML 保存時のエラーにはしない。

検証エラーは読み込み時に一覧表示し、可能であれば該当ノードへ移動できるようにする。

## 12. テスト方針

Core 層を中心にテストする。

- ID 採番
- YAML 読み込み
- YAML 保存
- 読み込み後に保存して構造が維持されること
- 必須項目検証
- 上限件数検証
- 親子関係検証
- 関連下位要求の参照検証
- 自動レイアウトが同一入力から同一配置を再現すること
- ID セグメントの数値昇順で背景と兄弟ノードが並ぶこと。特に `999` が `1000` より前になること
- 背景、上位要求、下位要求、仕様が左から右へ配置され、ノード矩形が重ならないこと
- 親子接続線がすべて親の下辺中央から子の左辺中央へつながり、始点で下向き、終点で右向きになること
- 複数の子、長文、理由展開、サイズ補正後もアンカーがノード境界へ追従し、曲線がノード内部を横切らず描画範囲で切れないこと
- 予測サイズだけで初回レイアウトできること
- 有効な DOM 実測値がある場合に予測値より優先されること
- 実測高さとの差が `max(8px, 予測高さの10%)` を超える場合だけ補正されること
- `LayoutRevision`、ノード幅、理由展開状態の変更で該当する実測キャッシュだけが無効になること
- ノード変更時に影響サブツリーだけを再計算し、影響外の配置が不必要に変化しないこと
- ポインター中心ズームで注目していたキャンバス座標が同じビューポート位置に維持されること
- ズーム操作が10%単位で25%から200%へクランプされること
- ズーム、パン、理由展開状態が YAML 保存・読み込みで復元されること
- ビュー状態のない旧 YAML が既定のビュー状態で読み込めること
- USDM 表への変換結果が要求・理由・仕様の関係を保持すること
- 理由未入力時に YAML 保存は成功し、エクスポート時だけ警告されること
- 同じ文書を繰り返し保存しても YAML のバイト列が変わらないこと
- 現在のソフトウェアバージョンが `version` に保存されること
- 現行の YAML 形式バージョンが `format_version` に保存されること
- `version` の変更だけでは読み取り形式の選択が変わらないこと
- `format_version` に対応する旧 YAML を現在の内部モデルへ変換できること
- `format_version` のない旧 YAML を形式バージョン1として読み込めること
- 変換後に保存すると `version` と `format_version` がそれぞれ現在値へ更新されること

初期段階では Core 層の単体テストを優先し、UI 操作は手動確認で進める。キャンバス操作が安定した段階で Playwright による主要操作の UI 自動テストを追加する。

性能面は100、500、1,000、2,000ノードの測定用データで描画、自動レイアウト、追加、編集、ズーム、パン、YAML 読み書き、FPS、メモリ使用量を計測する。一次性能評価環境は macOS / Apple Silicon M2 / 16GB / Google Chrome 最新安定版とし、Safari 最新版は互換性と実動作を確認する。Edge と Firefox は v1.0 の厳密な性能保証対象に含めない。

2,000ノードでは連続操作の60fps、平均45fps以上、30fps未満が継続しないことを設計上の初期目標とし、正式な保証値は実測後に確定する。メモリは起動直後、2,000ノード読み込み後、操作後、文書クローズ後に測定し、読み込みとクローズ、編集と Undo / Redo、追加と削除の反復で一方向に増加し続けないことを確認する。絶対上限値は実測結果から別途決定する。10,000ノード以上では、全件描画ではなく YAML の保存・読み込み完了とデータ欠落がないことを確認する。

## 13. バージョニング方針

アプリケーションの SemVer と YAML 形式バージョンは独立して管理する。

- YAML の `version` は最終保存時の Application Version を記録する。
- YAML の `format_version` は YAML 構造の互換性判定と読み取り用クラスの選択に使用する。
- アプリケーション機能だけの追加では `format_version` を変更しない。
- YAML 構造に互換性上意味のある変更がある場合だけ `format_version` を更新する。
- `view` 状態の永続化を初めて導入するリリースは Application Version の Minor を上げる。具体的な番号はリリース計画で決定する。
- `view` を追加した形式は形式バージョン2とし、`format_version` がない既存形式を形式バージョン1として読み込む。

保存時は実行中の Application Version と現行 `format_version` をそれぞれ出力する。読み込み時は `format_version` を先に判定して現在の内部モデルへ変換し、`version` は作成・保存元アプリケーションの識別と診断情報として扱う。
対応可能な `format_version` であれば、`version` が現在の Application Version と異なることだけを理由に読み込みを拒否しない。
