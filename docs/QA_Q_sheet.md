## 1. 目的と回答方法

本書は、既存設計と現行実装をもとに、たなかさん側で判断する利用上の仕様、UI評価、試験条件、受け入れ条件を整理する。質問番号は本票専用であり、Issue番号ではない。

- `D-*`: 設計判断。先行回答を優先し、UI比較が必要な項目は評価後に回答する。
- `T-*`: 試験設計と試験後の判断。実施前に条件を決め、実施後に結果を追記する。
- `F-*`: 将来対応。v1.0の着手を止める回答必須項目にはしない。
- 候補と推奨案は未採用の案である。回答は「未回答」「回答済み」「評価待ち」「保留」で管理する。
- 数値や方針を変更する回答には理由を記載する。回答の設計書反映は別作業として行う。

実装方法、キャッシュ構造、クラス構成、測定コードの作成は開発側が担当する。たなかさんには利用者としての必要性、許容範囲、評価結果、採用する方針を回答いただく。

## 2. 判断の前提

次は決定済みであり、本票で再選択を求めない。

| 項目 | 既存方針 |
|---|---|
| 階層 | 背景 → 上位要求 → 下位要求 → 仕様。各ノードの親は1つ |
| 配置 | 親の下へ右にインデントする自動レイアウト。子の左辺を親の中心と右端の中間へ揃える。背景本体からツリー全体をドラッグ可能。個別ノード移動・手動並べ替えは対象外 |

| 配色・線 | 背景は青、要求は緑、仕様は黄、文字と枠は黒、キャンバスは白。親の下辺中央から子の左辺中央へベジェ曲線で接続 |

| 高さ予測 | 1行18文字は予測係数であり入力制限ではない。操作領域32pxは初期設定値 |

| 保存 | ブラウザダウンロードによるYAML保存。背景位置だけを保存し、子孫座標・実測サイズ・未確定移動候補は保存しない |

現行コードでは、280px、18文字、操作領域32px、最低高さ110px、数値ID順、ズーム・パン、Coreでの形式1・2とビュー状態の入出力が実装されている。親の下へ右にインデントする配置と、その位置関係に対応する下辺・左辺アンカーの曲線計算、縦10pxの楕円からの子追加、理由操作に対する子追加の優先制御、ツールバーからの背景追加も実装・検証済みである（D-14の記録参照）。一方、画面の新規・開く・ファイル保存などのボタンには処理が接続されておらず、編集・削除・検索・Undo / Redo・エクスポートを含む実UI試験はこれから実施する。追加ダイアログの「保存」は実行中の文書へ確定する操作であり、YAMLファイルの保存ではない。局所再計算、カリングと2,000ノードの正式性能試験も未実施である。

今回追加した空白ダブルクリック、背景ドラッグ、ツリー間重複制御、背景位置保存と形式3は設計事項であり、現行コードには未実装である。以下に保持する形式2での追加・配置・強調制御の合格記録を、今回の受け入れ結果へ流用しない。

## 4. 設計判断

### D-01 ID欠番の再利用

現状は「未使用の最小IDを採番」が#028の暫定方針であり、コードと単体テストもこの挙動である。欠番再利用と、削除済み番号を再利用せず新規IDを増やす方針のどちらを正式採用するか。Git履歴や文書外からIDを参照する運用があるかも記載する。

再利用しない場合は、最大IDのノード削除後やYAML再読込後も再利用しないことが必要か。必要なら過去の最大採番値を保持する設計が必要となる。採番範囲の上限到達時に、追加を停止して通知する扱いでよいか。

### D-02 YAML互換性と未知項目

未対応の将来`format_version`を「エラー」「読み取り専用」のどちらで扱うか。現行実装は未対応形式をエラーとする。v1.0はこの扱いを維持する案を推奨する。

`version`欠落、対応形式内の未知キー、存在しないノードを参照するビュー状態を、拒否・警告・既定値補完のどれで扱うか。未知キーは現行デシリアライザーが無視するため、再保存による情報欠落を許容するか判断が必要である。`format_version`未記載を形式1、`view`未記載を既定ビューとする方針は決定済み。

### D-03 USDM表の形式と行・列

v1.0の出力を`.xlsx`、`.csv`、両方のどれにするか。背景、上位要求、上位理由、下位要求、下位理由、仕様、各ID、関連要求をどの列・シートへ出すか。

1仕様1行とするか、仕様を持たない要求や上位要求だけの項目も出すか。関連要求はIDのみか本文も含めるか。希望する実例を1つ作成いただくと、実装と試験の正解データに使用できる。

### D-04 Undo / Redoの範囲と単位

追加、編集、配下削除、貼り付け、関連要求変更を履歴対象とするか。編集は入力文字ごとか、ダイアログ保存1回ごとか。親削除は配下を含めて1回のUndoで復元する案を推奨する。

新規・読込・保存による履歴リセット、Undo後に別編集を行った場合のRedo破棄、履歴件数上限を決める。初期案は「新規・読込でリセット、保存では維持、編集確定ごとに1件」である。上限はメモリ試験も参考にする。

背景のドラッグ1回を1件とするか、追加・編集・理由展開に伴う他ツリー自動移動を元操作と一緒に復元するかも判断する。無効・取消のドラッグを履歴へ追加しないことは今回の設計で定義した。

### D-05 未保存確認と保存済み判定

本文変更がある場合の新規・読込・タブ終了・再読込で、確認を表示するか。新規・読込は「保存して続行」「破棄して続行」「キャンセル」のどこまで提供するか。

ブラウザダウンロード方式で、アプリが何を完了した時点を「保存済み」と表示するか。保存前にキャンセルした場合やダウンロード生成が失敗した場合の扱い、ファイル名と未保存表示の位置も決める。破壊的な文書切り替えは、キャンセルで元の文書を維持する案を推奨する。

### D-06 ビュー状態変更の扱い

ズーム、パン、理由展開はYAML保存対象だが、これらだけの変更でも未保存マーク・離脱確認を出すか。本文変更とビュー変更を区別して表示する案も候補である。

ビュー操作をUndo / Redoに含めるか、別管理するか。ビュー操作後すぐ保存した場合に直前の状態まで復元することを、受け入れ条件に含めるか。保存対象のビュー項目そのものは変更しない。

背景位置の有効な移動・自動移動は保存対象の変更として扱い、無効・取消では新たな変更を作らない。これは今回の確定方針とし、上記のズーム・パン・理由展開だけの未保存判定と区別する。

### D-07 本文・理由の長さと入力

背景、要求、理由、仕様それぞれの想定通常長・最大長を示す。最大長を制限するか、実用上の評価範囲だけ定めるか。改行、日本語IME、英数字、URLなど長い連続文字列の利用例はあるか。

長文は全文表示を基本とし、特に理由は展開時に全文表示する既存方針を維持する。本文の省略表示やノード内スクロールが必要なら別の変更要求として記載する。18文字を入力制限にしない。

### D-08 検索条件と結果への移動

部分一致か完全一致か、英字大小文字・全角半角・空白を区別するか、複数語はANDかORか。日本語中心の単純な部分一致を初期案とする。

結果を選んだ際に、強調表示だけか、対象が見える位置までパンするか。ズーム倍率を維持するか、理由一致時に理由を展開するか。検索対象にID・背景を追加する質問ではなく、確定済みの要求・理由・仕様の範囲内で決める。

### D-09 コピー範囲と貼り付け先

選択ノード1件だけか、サブツリー全体をコピーするか。貼り付け先の親は選択中ノードで指定するか。親の種類が合わない場合は拒否するか。

複製IDの新規採番、コピー範囲内の関連参照の付け替え、範囲外への参照維持、ビュー状態のコピー範囲を決める。macOSの`Cmd+C` / `Cmd+V`と、入力欄での通常の文字コピーが競合しないことを試験対象にする。

### D-10 削除に伴う関連参照の扱い

下位要求を削除した際、別サブツリーの仕様からその要求へ関連参照がある場合に、参照だけ除去するか、削除を拒否して整理を求めるか。

配下全削除と初回確認・確認省略は決定済みである。残る仕様を関連参照だけを理由に削除しない案を推奨する。参照除去、ビュー状態の整理、配下削除を1回のUndoで復元するかもD-04と合わせて決める。

### D-11 読込失敗時の文書保護

構文不正、親参照不正、未対応形式などで読込が失敗した場合、元の文書とビュー状態を維持してエラー一覧を出す扱いでよいか。部分的に正常なノードだけを取り込む機能はv1.0で必要か。

初期案は文書単位で検証を完了してから切り替える。エラーのファイル名・項目・IDをどこまで表示すれば修正できるかも回答する。

### D-12 再配置コマンドと操作後の注目位置

自動レイアウトに加えて、明示的な「全体自動整列」をv1.0に用意するか。追加・編集・削除後に選択状態とズームを維持するか、追加ノードが見えるようにパンするか。

通常操作で影響外ノードを不必要に移動させない方針は決定済み。必要な重複回避のために兄弟や祖先側へ影響が広がる場合、どのような移動なら許容できるかを実例で示す。

### D-13 共通幅の正式決定

同じデータ・フォント・画面・ズームで240 / 280 / 320pxを比較し、正式幅と採用理由を回答する。短文、2〜3行の要求、長文、長い理由、英数字、4階層表示を対象とする。

最低高さ110pxは維持する。文字切れ・操作UIとの重なりがないこと、可読性、ノード高さ、4階層の横幅、画面内情報量を比較する。280pxの実装済みだけを理由に正式採用しない。

### D-14 表示品質と画面変化への対応

日常使用する画面サイズ、macOSの表示設定、ブラウザ表示倍率で評価し、文字・操作ボタン・理由表示・接続線が読みやすいか。左右余白16px、上下余白12px、行高22px、ID領域24px、項目間隔8pxはUI評価で調整する暫定値である。

#### 背景追加・ツリー全体移動の受け入れ項目（今回設計、未実施）

- 空白の主ボタンダブルクリックで1つだけ入力ダイアログが開く。単一クリック、パン後、ノード・楕円・線・操作部品上では誤追加しない。透明SVG領域は空白として扱う。
- 25%・100%・200%とパン後に、クリックしたキャンバス位置が背景左上へ対応する。入力保存時だけ背景と位置が確定し、キャンセル・入力エラーで文書・位置・採番が変わらない。
- 背景本体からのドラッグで背景・全子孫・曲線が同量移動し、内部配置・接続面・ID・兄弟順を保つ。背景単独と4階層、多数子孫を含める。
- 子追加楕円を背景ドラッグより優先する。楕円からドラッグ・キャンセルしてもツリー移動や理由操作へ切り替えず、青い楕円の古いホバーも残さない。
- ツリー外接矩形の内部が重なる位置では移動不可表示となり、離すと最後の有効候補ではなくドラッグ開始位置へ全体が戻る。他ツリーのノード・曲線は不変。境界接触と線だけが張り出す場合も区別する。
- Escape・ポインターキャンセル・キャプチャ喪失・非アクティブ化で開始位置へ戻る。無効・取消・実質移動なしでは背景位置・未保存判定・履歴を変更しない。移動中の保存に候補を混入させない。
- 子追加・本文編集・理由展開・DOMサイズ補正で他ツリーが重なる場合は、操作元を固定して他ツリーを自動移動する。複数背景への連鎖、非衝突ツリーの不変、縮小時に詰め直さないこと、自動移動位置の保存を確認する。
- 形式3の保存・再読込で背景位置、ズーム、パン、理由状態を独立して復元する。形式1・2、位置の一部欠落、負座標、不正値、重複する保存位置の読込補正と通知を含める。画面外・将来カリングされたノードも重複判定対象から失わない。

重複範囲と自動移動の暫定解法は [LayoutDesign.md](LayoutDesign.md) §7を参照する。操作の合否と、下方押し出しの見やすさ・移動量に対する評価を分け、結果は実装後に追記する。以下は以前の機能の検証履歴として保持する。

親の下へ子を配置し、子の左辺が親の中心と右端の中間へ揃うことを評価する。複数兄弟の左辺が揃い、先の兄弟に深い子孫があっても、次の兄弟がそのサブツリー全体の下へ配置されることを確認する。接続線は親の下辺中央から子の左辺中央へ入り、長文・理由展開時もノードを横切らず表示範囲で切れないことを確認する。これらの配置・接続規則は決定済みであり、評価は読みやすさと形状の調整を対象とする。

子追加UIは、下辺中央を中心とする縦10 CSS px・横が下辺の1/4〜3/4の楕円を対象に、25%・100%・200%とパン後も縦寸法と横の比率が一致することを評価する。中心、上下左右の境界、境界直外、外接長方形の四隅を確認し、長方形として誤判定しないことを確認する。ホバー・フォーカス時の形状も判定範囲と一致させる。

理由展開部と重なる楕円の上側をクリックした場合は、子追加ダイアログだけが開き、理由の展開・折りたたみ状態が変わらないことを確認する。楕円外の理由クリックは有効であること、ドラッグやキャンセルで理由操作へ切り替わらないこと、接続線起点、長文・理由開閉後の追従、正しい子種別、キャンセル・連打の誤追加防止、キーボード操作も確認する。楕円形状と優先制御は実装・再試験済みであり、以下へ旧4px帯とは区別して記録する。

#### 追加後の楕円強調の残留（2026-10-27実装・Safari一部確認）

### T-07 YAML・表出力の正解データ

D-03の列・行に対応した期待出力と、形式1・2・背景位置対応形式3の代表YAMLを用意する（現行実装は2まで）。保存→読込→再保存で本文、親子関係、関連要求、背景配置位置を含むビュー状態が一致することを確認する。

要求を編集した差分、ビューだけの差分、形式1・2→3変換時の差分の許容範囲を決める。背景移動では当該背景位置だけ、自動移動では影響した背景位置だけが変わり、子孫座標が出力されないことを確認する。変換後の現行形式を同じApplication Versionで保存する場合に、不要なキー順・改行差分が生じないことを確認する。表出力は日本語、改行、理由空欄、仕様なし要求、関連参照を含む例を、実際に使用する表計算ソフトで確認する。

### T-08 境界値・異常系・復旧

必須確認候補は、空文書、単一ノード、本文空欄、理由空欄、長文、IDの001・999・1000・65535と上限超過、同一IDの背景と要求、親ID不正、未知形式、YAML構文不正である。ID上限試験はCoreを中心に行い、65535ノードの快適なUI描画を求めない。

配下全削除、確認省略設定、関連参照整理、Undo復元、ダイアログのキャンセル、読込失敗、保存失敗、未保存の文書切り替えを確認する。ローカルサーバー停止・再接続時に、編集中データがどうなることを受け入れ条件とするか。v1.0に再起動をまたぐ自動復旧が必要なら追加要求として明記する。

### T-09 Safari確認とUI自動テスト

Safariで確認する最低シナリオを選ぶ。パン・ズーム・理由展開、IME入力、macOSショートカット、ファイル読込・ダウンロード、再読込したビュー、ダイアログと削除確認を候補とする。

手動確認後、キャンバス操作が安定した段階でPlaywrightへ移す優先シナリオを決める。Core単体テスト済みだけで画面合格にせず、ブラウザからの一連の操作を確認する。自動テストのWebKit結果と実Safariの確認結果は区別する。

### T-10 性能結果の採否と#022 Close

T-03〜T-06の実測後に、初期目標を正式保証値として採用できるか回答する。未達項目は原因調査・改善・再試験を基本とし、目標変更が必要なら利用上の許容範囲と理由を記録する。

2,000ノードの目標未達時にカリングをv1.0へ導入するか、別の改善で再試験するか。#022のClose判断は、2,000ノードの実UI結果、10,000ノード以上のYAML往復と欠落なし、ChromeでのFPS・メモリ結果、Safari実動作、正式保証値・カリング要否の決定を根拠に行う。未実施項目を合格扱いにしない。

## 6. 将来対応として保留できる事項

### F-01 手動配置と並べ替え

背景単位の配置保存とツリー全体移動は今回の初期版設計へ移した。ここで保留するのは個別ノードの手動配置・並べ替えである。実使用後、個別座標の保存、背景以外の親を移動する際の子の追従、自動配置との優先順位、自動へ戻す操作、`displayOrder`の割り当てを検討する。ツリー内部は自動配置・兄弟ID順を維持する。

### F-02 サブツリー折り畳みとFit操作

実使用後、理由の折りたたみとは別に子孫を隠す機能、Fit All、Fit Selectionが必要か判断する。折り畳み保存、検索時の展開、展開時の注目位置を検討する。現行の将来対応という位置づけを維持する。

### F-03 配布・連携・出力拡張

v1.0の利用感を確認後、self-contained配布、Google Drive連携、配色設定、画像・PDF・Markdown出力などの優先順位を決める。必要になる時期と利用例だけを記録して保留してよい。
